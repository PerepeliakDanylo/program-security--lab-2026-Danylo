Автентифікація (ЛР4) доводить, **хто** супроводжувач; цей документ визначає, **що** кожному
автентифікованому супроводжувачу дозволено, і як це примусово забезпечується.

## 1. Суб'єкти, ресурси, операції

- **Суб'єкти:** автентифіковані супроводжувачі, кожен має одну чи кілька **ролей**.
- **Ресурси:** сховище облікових записів, окремі записи, реліз-кандидат (збірка для підпису).
- **Операції під контролем:** `list-users`, `add-user`, `set-role`, `passwd`, `build-manifest`,
  `sign`, `rotate-key`, `verify`, `enroll-totp` (з ЛР6). Команди `help`, `whoami`, `status` нічого не змінюють і не
  розкривають чужого — їм роль не потрібна.

## 2. Обрана модель — змішана, з обґрунтуванням

Жодна окрема модель не підходить повністю, тож використано **змішану** (методичка це дозволяє):

| Рівень | Для чого | Чому |
|---|---|---|
| **RBAC** (база) | які операції суб'єкт узагалі може викликати | Мало суб'єктів, типові обов'язки — ролі природні й легкі в супроводі |
| **ABAC** (умови) | `sign` — лише чистий `master`; критичні операції — лише зі **свіжим** підтвердженням пароля | Частина рішень залежить від **ресурсу й контексту**, а не лише від ролі |
| **DAC** (одне правило) | користувач може змінити **власний** пароль | Володіння власними обліковими даними — дискреційне, не рольове |

Мандатну модель (MAC, мітки секретності) не застосовано: в інструменті немає даних різних рівнів
секретності, які треба розділяти за мітками; її поява була б надмірністю без загрози, яку вона
закриває.

## 3. Ролі (найменші привілеї)

Упорядковані, кожна успадковує нижчі (`viewer ⊂ contributor ⊂ maintainer ⊂ owner`):

| Роль | Додає | Кому |
|---|---|---|
| `viewer` | лише читання: `list-users`, `verify`; власний другий фактор `enroll-totp` (з ЛР6) | аудитор, співавтор на читання |
| `contributor` | `build-manifest` (підготовка збірки) | той, хто готує збірку, але **не** підписує |
| `maintainer` | `sign` (випуск збірки) | той, хто підписує реліз |
| `owner` | `add-user`, `set-role`, `rotate-key` | власник проєкту, адміністратор записів і ключів |

Нові записи отримують **найнижчу** доречну роль; базова — `viewer` (і значення за замовчуванням
у сховищі). Перший `owner` створюється один раз через **бутстрап**: CLI-`add-user` працює лише для
порожнього сховища, далі записи додає тільки `owner` у сесії. Сховище тримає інваріант, що не
залежить від того, хто питає: **останнього `owner` неможливо позбавити цієї ролі** — інакше ніхто
більше не зміг би керувати записами.

## 4. Атрибути в рішеннях

- **Суб'єкт:** `roles`.
- **Ресурс (реліз-кандидат):** `branch`, `dirty` (є незакомічені зміни). У ЛР5 — з
  `release.state.json`; ЛР7 бере їх із реального `git`. Невідомий чи відсутній стан =
  `dirty=True` → **безпечна відмова**.
- **Контекст:** вік останнього підтвердження паролем (step-up) у секундах.
- **Володіння (DAC):** для `passwd` — чи є цільовий запис записом того, хто викликає.

## 5. Правила доступу

| Операція | RBAC (мін. роль) | Умова ABAC / DAC |
|---|---|---|
| `list-users`, `verify` | viewer | — |
| `enroll-totp` | viewer | лише власний запис; свіже підтвердження; підключення — лише з правильним кодом із застосунку (з ЛР6) |
| `build-manifest` | contributor | — |
| `sign` | maintainer | `branch == master` **і** `dirty == False`; свіже підтвердження |
| `add-user`, `set-role`, `rotate-key` | owner | свіже підтвердження |
| `passwd` | — (DAC) | цільовий запис — свій, **або** той, хто викликає, — `owner`; свіже підтвердження |

**Step-up:** критична операція (`sign`, `add-user`, `set-role`, `rotate-key`, `passwd`, `enroll-totp`), якщо від
останнього введення пароля минуло понад 5 хв (`authz.STEPUP_WINDOW_S`), просить пароль ще раз. Це
не остаточна відмова: правильний пароль — операція виконується; невірний — відмова й запис у журнал.

## 6. Примусове забезпечення

- Рішення приймає **одна** функція — `authz.authorize()`, **вкомпільована в інструмент** і не
  налаштовувана з жодного файла: політику неможливо послабити ззовні (SR-25).
- Кожна захищена команда викликає `guard()` → `authorize()` **безпосередньо перед дією**, у точці
  виконання, а не ховаючи пункт меню. Команду, недоступну ролі, можна набрати — обробник однаково
  її відхилить (SR-24). Альтернативного шляху «повз меню» немає.
- У разі відмови користувач бачить лише загальне «Операцію відхилено.»; конкретна причина (`rbac`,
  `abac-dirty`, `not-owner`, `stepup-failed`) і кожен дозвіл (`authz-allow:*`) пишуться в журнал
  аудиту (SR-26).

## 7. Трасування вимог

| ID | Вимога (коротко) | Де виконано |
|---|---|---|
| FR-73 | Операції авторизуються за роллю (RBAC) з найменшими привілеями; останній `owner` лишається | `authz.permissions_for`, `accounts.set_roles` |
| FR-74 | Підпис — лише для чистого `master` | `authz.authorize` (ABAC для `sign`) |
| FR-75 | Критичні операції потребують свіжого підтвердження (step-up) | `authz.CRITICAL`, `drs_release.require_step_up` |
| FR-76 | Змінити пароль можна лише свій, крім `owner` (DAC) | `authz.authorize` (`passwd`) |
| SR-24 | Перевірка прав — у точці виконання операції, не приховуванням інтерфейсу | `drs_release.guard` у кожному обробнику |
| SR-25 | Політика доступу вкомпільована й не розширюється з конфігурації | `authz._BASE` (жодного файлового входу) |
| SR-26 | Відмова для користувача загальна; причина — лише в журналі | `guard` → `store.audit` |

## 9. Перевірені сценарії

Перевірено і дозволені, і заборонені шляхи; відмова не залежить від способу виклику:

- `viewer` → `sign`, `add-user` відхилено (RBAC); `list-users` дозволено.
- `maintainer` → `sign` відхилено, поки `release.state.json` брудний або не `master` (ABAC);
  дозволено при `branch=master`, `dirty=false`.
- `passwd` на **власний** запис — дозволено (DAC), на чужий без ролі `owner` — відхилено.
- Критична операція після вікна step-up → повторний запит пароля; невірний → відмова.
- `set-role owner1 viewer`, коли `owner1` — єдиний власник, → відмова з поясненням.

## 10. Відкладено

Тіла `sign`, `build-manifest`, `verify` (маніфест + Ed25519) — ЛР7; `rotate-key` (конверт секрету
TOTP) — ЛР6. ЛР5 керує **доступом** до них.
