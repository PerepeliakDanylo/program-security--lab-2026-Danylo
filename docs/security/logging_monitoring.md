## 1. Що реєструється (п. 9)

| Подія | Рівень | Журнал | Навіщо |
|---|---|---|---|
| `server.started` / `server.stopped` / `server.start_failed` / `server.insecure_http` | INFO / ERROR / WARNING | обидва | хто й коли запускав, з якою версією, TLS, функціями |
| `http.access` — кожен запит: метод, маршрут, шлях, статус, байти, мс, адреса, клієнт, відбиток токена, User-Agent | INFO | загальний | відтворення послідовності, розміри відповідей (оцінка витоку), розвідка й перебір |
| `auth.token_issued` / `auth.token_revoked` | INFO | обидва | хто отримав доступ, із яким скоупом, відбиток токена |
| `auth.denied` — причина, `client_id_attempt`, блокування | WARNING | обидва | невдалі входи й відмови авторизації (у Libraxis їх не було взагалі) |
| `release.published` | INFO | обидва | критична зміна даних: хто, яка версія, SHA-256 запису |
| `admin.command` — команда, ціль, результат, користувач ОС, хост | INFO / WARNING | обидва (файли `*-admin-*`) | аудит адміністрування (лише локальне) |
| `ops.metrics_read` | INFO | загальний | хто читає стан сервера |
| `http.unhandled` (тип винятку), `http.protocol_error`, `http.connection_error` | ERROR / WARNING | загальний | помилки ПЗ без витоку подробиць клієнту |
| `tls.handshake_failed` | WARNING | обидва | невірні клієнти, сканування |
| `alert.raised` — правило, суб'єкт, кількість, вікно | WARNING / CRITICAL | обидва | спрацювання порогів моніторингу |
| з ЛР13–14: `report.*`, `ledger.*` | INFO / WARNING | обидва | звіти тестерів, журнал релізів |

**Не реєструється**: тіла запитів, заголовок `Authorization`, секрети, токени, вміст звітів тестерів.

## 2. Структура запису

JSON Lines: один рядок — одна подія, однакова схема для всіх подій компонента.

| Поле | Опис |
|---|---|
| `ts` | UTC, ISO 8601 з мілісекундами й `Z` (`2026-11-18T12:04:02.317Z`) — одна часова основа |
| `level` | `DEBUG` / `INFO` / `WARNING` / `ERROR` / `CRITICAL` |
| `event` | назва `домен.дія` (каталог — §1) |
| `component`, `version`, `host`, `pid` | хто записав: `drs_hub` або `drs_hub.admin`, версія коду, хост, процес |
| `request_id` | 16 hex; той самий у `X-Request-ID` відповіді й у кожній події запиту |
| `ip`, `client_id`, `token_fp` | джерело, суб'єкт, відбиток токена (12 hex SHA-256) — розрізняє два токени одного клієнта |
| поля події | `route`, `method`, `status`, `bytes`, `ms`, `reason`, `scope`, `version`… |
| `prev`, `chain` | лише безпековий журнал: ланцюг SHA-256 (§6) |

## 3. Рівні

`DEBUG` — діагностика розробки (вимкнено за замовчуванням); `INFO` — нормальні значущі події;
`WARNING` — відмови й нетипові ситуації без відмови сервісу; `ERROR` — збій окремої операції;
`CRITICAL` — загроза працездатності сервісу (сплеск `5xx`). Однакові за вагою події завжди мають
однаковий рівень.

## 4. Атрибути для зіставлення подій

`request_id` (запит ↔ усі його події ↔ відповідь клієнту), `client_id` + `token_fp` (суб'єкт і
конкретний токен), `ip`, `ts` (UTC). `python hub_monitor.py trace <request_id>` збирає всі події
запиту з обох журналів.

## 5. Чутливі дані, яких у журналі немає (п. 10)

Паролі, секрети клієнтів (`dhs_…`), токени доступу (`dha_…`), заголовок `Authorization`, закриті
ключі, тіла запитів, вміст звітів тестерів. Механізми: (1) сервер передає в журнал лише відбиток
токена; (2) `hub_log.redact` замінює поля з чутливими іменами й значення, схожі на токен, секрет,
`Bearer …` чи PEM ключа, на `[REDACTED]`; (3) рядки обрізаються до 300 символів, керувальні символи
екрануються JSON — підробити рядок журналу через поле запиту не можна; (4) `hub_monitor.py verify`
і самоперевірка шукають шаблони секретів у всіх файлах журналу.

## 6. Зберігання, ротація, захист (п. 10)

| Файл (у `<тека даних>/logs/`) | Вміст | Ротація | Зберігання |
|---|---|---|---|
| `hub-YYYY-MM-DD.jsonl` | усі події рівня ≥ `log_level` | щодоби (UTC) | 14 діб |
| `security-YYYY-MM-DD.jsonl` | лише безпекові (`auth.`, `admin.`, `release.`, `report.`, `ledger.`, `alert.`, `tls.`, `server.`) | щодоби | 90 діб |
| `hub-admin-…`, `security-admin-…` | те саме від `hub_admin.py` (окремий процес — окремий ланцюг) | щодоби | 14 / 90 діб |

- Тека даних — поза репозиторієм (`%USERPROFILE%\.drs_hub`), права — ACL профілю власника.
- **Ланцюг SHA-256** у безпековому журналі: кожен запис містить `prev` (хеш попереднього) і
  `chain = SHA-256(prev ‖ канонічний JSON запису)`. Зміна, вставка чи видалення рядка ламає ланцюг
  (`hub_monitor.py verify` називає рядок). Після перезапуску сервера ланцюг продовжується з
  останнього запису файла; пошкоджений хвіст — явна позначка `chain_restart`.
- Старші за строк файли видаляються автоматично при відкритті нового дня. Безпекові журнали
  входять у резервні копії (ЛР15).

## 7. Показники й сповіщення (моніторинг)

`GET /api/v1/metrics` (скоуп `metrics:read`): час роботи, запити за класами статусів і маршрутами,
відмови `401/403/429`, невдалі автентифікації, видані токени, затримка p50/p95/max, вікно 5 хв, останні
сповіщення; стан бази (клієнти, активні токени, релізи, `integrity_check`), обсяг теки журналів.
`python hub_monitor.py metrics --watch N` — періодичне опитування з позначками «УВАГА» / «КРИТИЧНО».

| Правило | Поріг | Рівень | Що ловить (Libraxis) |
|---|---|---|---|
| `auth.bruteforce_ip` | ≥ 10 невдалих автентифікацій з адреси за 60 с | WARNING | 20 × `401` за хвилину з однієї адреси |
| `auth.lockout` | блокування `client_id` (5 невдач) | WARNING | підбір пароля одного запису (`shelby`) |
| `authz.denied_burst` | ≥ 10 × `403` одному суб'єкту за 60 с | WARNING | спроби дістатися чужих ресурсів |
| `http.scan_404` | ≥ 20 × `404` одній адресі за 60 с | WARNING | перебір `/admin`, `/swagger`, `/docs`… |
| `http.error_burst` | ≥ 5 × `5xx` за 60 с | CRITICAL | масові `500` після `DROP DATABASE` |
| `tls.handshake_burst` | ≥ 20 невдалих рукостискань за 60 с | WARNING | сканування порту, невірні клієнти |

Повтор того самого сповіщення — не частіше разу на 5 хв (без «шторму»). Пороги моніторингу
`hub_monitor.py metrics`: `5xx` за 5 хв > 0, невдалих автентифікацій за 5 хв ≥ 10, p95 > 500 мс,
`integrity_check` ≠ `ok`.

## 8. Уроки Libraxis → рішення

| Недолік журналу Libraxis | Рішення в `drs_hub` |
|---|---|
| Сім форматів часу без пояса | один формат UTC ISO 8601 + `Z` |
| Немає адреси, клієнта, ідентифікатора запиту | `ip`, `client_id`, `token_fp`, `request_id` у кожному записі запиту |
| Невдалі входи не реєструються | `auth.denied` з причиною, `client_id_attempt`, блокуванням |
| Один `uid` для двох суб'єктів | `token_fp` розрізняє токени; новий токен — подія `auth.token_issued` з адресою |
| Експорти без суб'єкта й розміру | події критичних операцій з суб'єктом і SHA-256; розмір — у записі доступу |
| Помилка SQL без контексту, детальна помилка клієнту | `http.unhandled` з типом винятку в журналі, клієнту — загальна помилка з `request_id` |
| Багаторядкові стеки | один рядок JSON на подію |
| Немає сповіщень | 6 правил порогів, `alert.raised`, `/api/v1/metrics` |
| Нападник читав і міг правити журнал аудиту | безпековий журнал із ланцюгом SHA-256, поза мережевим доступом |
