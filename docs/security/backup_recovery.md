## 1. Що потрібно для відновлення, а що відтворюється (п. 3)

| Дані / компонент | Де | Резервувати? | Чому |
|---|---|---|---|
| База сервера `drs_hub.db` (клієнти — SHA-256 секретів, релізи, звіти тестерів — шифротекст, хеш-ланцюг) | тека даних `%USERPROFILE%\.drs_hub` | **так** | унікальні дані; звіти й ланцюг не відтворити |
| `hub.json` (несекретні налаштування) | тека даних | так | швидке відновлення конфігурації |
| TLS: `ca_cert.pem`, `server_cert.pem`, `server_key.pem` | `tls/` теки даних | так | без них клієнтам потрібен новий CA (`ca_cert.pem`) |
| Безпекові журнали `security*.jsonl` (90 діб) | `logs/` теки даних | так | розслідування інцидентів; ланцюг SHA-256 |
| **Закритий ключ отримувача звітів** `report_key.pem` (PKCS#8 під фразою) | `%USERPROFILE%\.drs_hub_keys` | **так, критично** | без нього всі звіти тестерів назавжди нечитабельні (сервер не допоможе) |
| Ключі релізу: `release_passport.key` (під фразою), `drs_release.signing.key` | профіль / тека інструмента | **так** | інакше — нові ключі й повторна публікація відкритих |
| Облікові записи `drs_release` (+ `.key` цілісності), журнал аудиту | тека інструмента | так | автентифікація супроводжувача й слід дій |
| Код, документи, історія | git + GitHub | **ні** | віддалений репозиторій — незалежна копія; відновлення = `git clone` |
| Збірки `build/`, `.asi`, архіви релізу | локально, NexusMods, GitHub Releases | ні | відтворюються з тегу; релізні файли ще й на майданчиках |
| Віртуальні середовища, кеші | `.venv` | ні | `pip install -r requirements.txt` |
| Загальний журнал `hub-*.jsonl` (14 діб) | `logs/` | ні | цінність низька; безпекові події — у `security-*` |
| Токени доступу, лічильники невдач | база | ні (очищаються в копії) | сеансовий стан: після відновлення клієнти беруть нові токени |

## 2. Стратегія (п. 4)

| Параметр | Рішення | Обґрунтування |
|---|---|---|
| Тип | **повна** копія щоразу | дані — кілобайти–мегабайти; інкрементні/диференційні копії не дають виграшу, а відновлення з одного файла найнадійніше |
| Періодичність | щодня (Планувальник завдань Windows) **+** після кожної публікації релізу **+** перед оновленням сервера | щоденна копія тримає RPO; події — точки, втрата яких найдорожча |
| Зберігання | GFS: 7 щоденних, 4 щотижневих, 6 щомісячних (`prune`) | вистачає, щоб повернутися до стану до непомітного пошкодження |
| Місце | правило 3-2-1: робоча тека + копії на **іншому диску** (`D:\DRS_backups`, `--dest`) + **офлайн**-копія щотижня (USB, від'єднаний) | відмова диска чи шифрувальник не знищить усі копії |
| Захист | AES-256-GCM, ключ — scrypt (N=2^15, r=8, p=1) від фрази ≥ 16 символів; параметри в автентифікованому заголовку | копія містить ключі й хеші — без фрази вона марна; фраза — у менеджері паролів + запечатаний папір, **не поруч із копіями** |
| Контроль цілісності | `<архів>.sha256` (без фрази) + тег GCM + маніфест SHA-256 кожного файла + `integrity_check` бази + перевірка хеш-ланцюга | пошкоджена чи підмінена копія виявляється до відновлення |
| **RPO** | ≤ 24 год (для релізів ≈ 0: копія після публікації + записи на Nexus і в git) | звіт тестера, втрачений за добу, тестер надішле повторно |
| **RTO** | ≤ 1 год до робочого сервера (саме відновлення — секунди, решта — перевірка й перенесення ключів) | службовий сервер; гра й мод від нього не залежать |

Щоденне завдання (один раз, PowerShell від імені власника):
```powershell
$py = "<REPO>\tools\drs_hub\.venv\Scripts\python.exe"
schtasks /Create /SC DAILY /ST 03:00 /TN "DRS Hub backup" /TR "`"$py`" `"<REPO>\tools\drs_hub\hub_backup.py`" create --dest D:\DRS_backups --profile %USERPROFILE%\.drs_hub\backup_profile.json --label daily"
```
(фраза — змінна `DRS_HUB_BACKUP_PASSPHRASE` облікового запису завдання або Диспетчер облікових даних; щотижня —
`hub_backup.py prune --dest D:\DRS_backups` і `verify --deep` останньої копії).

## 3. Процедури (п. 5–6)

**Створення:** `python hub_backup.py create --dest D:\DRS_backups --profile …\backup_profile.json [--label release-1-2-3]`.
Сервер може працювати: знімок бази — онлайн (SQLite backup API), без сеансового стану.

**Перевірка:** `verify <архів>` (SHA-256, без фрази) щодня; `verify <архів> --deep` (фраза: GCM, маніфест,
`integrity_check`, хеш-ланцюг) щотижня й перед відновленням.

**Відновлення (аварійне, нова машина):**
1. Встановити Python 3.10+, `git clone` репозиторію, `checkout` останнього тегу інструментів, `.venv` + `pip install -r requirements.txt`.
2. `python hub_backup.py restore <архів> --target %USERPROFILE%\.drs_hub` (сервер **зупинено** — тека блокується;
   наявна база відкладається в `pre-restore-<час>\`).
3. Перенести `restored_extra\*` на місця з `RESTORE_HINTS.txt` (ключ звітів, ключі релізу, файли `drs_release`), видалити теку.
4. `python hub_server.py`; `python hub_ledger.py verify`; голова ланцюга не старіша за останній якір у `docs/changelog.md`.
5. Клієнти автоматично отримують нові токени (сеансовий стан не відновлюється); якщо CA перевипускали — роздати новий `ca_cert.pem`.

**Регулярна перевірка відновлення:** раз на квартал — відновлення останньої копії в тимчасову теку
(`--target %TEMP%\drs_restore_test`), запуск сервера на іншому порту, `ledger-verify`, замір часу (RTO).

## 4. Результат перевірки в ЛР15–16

Копія `drs-hub-20261119-013425-lab15.dhbk` (`13 920` Б, `13` файлів), змодельовано втрату бази (видалено `drs_hub.db`), відновлено за `0.17` с (фактичний RTO `40` с); `integrity_check = ok`, ланцюг цілий, сервер стартував, клієнти отримали нові токени, реєстр релізів і звіти на місці.
