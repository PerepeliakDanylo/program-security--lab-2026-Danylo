## 1. Які дані потребують наскрізного шифрування (п. 6)

Супровід мода живе логами гравців: Markie98, jotaeli777, JackKiddArt надсилали `DynamicReloadSpeed.log`,
INI і перелік модів / дерево теки гри (Nexus, Discord). Лог плагіна шляхів не містить, але **перелік
модів і дерево теки** містять ім'я користувача Windows, склад ПК і встановлене ПЗ. Політика
конфіденційності мода обіцяє, що мод нічого не збирає; тож якщо тестер добровільно передає такий
пакет, бачити його повинен лише супроводжувач — не сервер, не його хостинг і не резервні копії.

| Питання методички | Рішення |
|---|---|
| 6.1 Між якими сторонами | Тестер (`hub_client.py submit-report`) → супроводжувач (`decrypt-report`); сервер `drs_hub` — посередник |
| 6.2 Де шифрується | На машині тестера, до відправлення (пакет: файли + примітка, стиснення zlib) |
| 6.3 Де розшифровується | Лише на машині супроводжувача, закритим ключем після введення парольної фрази |
| 6.4 Хто має ключі | Супроводжувач — закритий X25519 (PKCS#8, зашифрований фразою, поза репозиторієм); усі — відкритий (`tools/drs_hub/report_recipient.pub` у репозиторії); тестер — лише ефемерний ключ на один звіт (знищується); **сервер — жодного** |
| 6.5 Чого сервер не отримує відкрито | Вміст логів, INI, перелік модів, дерево теки, імена файлів, примітку |

Сервер бачить і зберігає лише **метадані**: `report_id`, автора (`client_id`), час, розмір, версію
плагіна й збірку гри, `kid` ключа отримувача — їх потрібно для маршрутизації, доступу й квитанцій.

## 2. Схема шифрування (п. 7)

```
тестер:   ефемерна пара X25519 (e, E)            супроводжувач: довготривала пара X25519 (r, R)
          shared = X25519(e, R)                                 shared = X25519(r, E)
          key    = HKDF-SHA256(shared, salt = E ‖ R, info = "drs-hub/report/v1", 32 Б)
          ct     = AES-256-GCM(key, nonce 96 біт випадковий, пакет, AAD = JSON{v, alg, kid, epk, meta})
конверт:  {v:1, alg:"X25519-HKDF-SHA256-AES256GCM", kid, epk:E, nonce, ct, meta}
```

| Властивість | Як забезпечено |
|---|---|
| Конфіденційність | AES-256-GCM; ключ виводиться з ECDH лише двома сторонами; у сервера немає закритого ключа |
| Цілісність і автентичність даних | Тег GCM: зміна шифротексту, nonce чи **метаданих** (AAD) → відмова розшифрування |
| Прив'язка до відправника | Сервер приймає звіт лише якщо `meta.submitter` = `client_id` токена (TLS + OAuth); `submitter` в AAD — підмінити автора після прийому непомітно не можна |
| Унікальність ключа й nonce | Новий ефемерний ключ на кожен звіт → новий ключ AES; nonce 96 біт випадковий (повтор пари ключ–nonce неможливий практично) |
| Розділення ключів | HKDF з контекстом `drs-hub/report/v1` і сіллю `E ‖ R` |
| Захист від підміни ключа отримувача | Відкритий ключ — у репозиторії, клієнт читає **локальний** файл і друкує `kid`; із сервера ключ не завантажується (інакше скомпрометований сервер підставив би власний) |
| Захист при розшифруванні | Розпакування ≤ 8 МіБ (бомба стиснення); імена файлів — лише базове ім'я з дозволеними символами, без пристроїв Windows (обхід шляху `..\..\` неможливий) |
| TLS | Лишається обов'язковим: ховає токени й метадані від мережі й автентифікує сервер (E2EE його не замінює) |

**Пряма секретність.** Ефемерний ключ тестера дає її з боку відправника; компрометація
**довготривалого** ключа отримувача розкриває всі звіти, зашифровані на нього. Пом'якшення:
ротація пари (новий `kid`; сервер приймає лише чинний `kid`), знищення старого закритого ключа після
обробки звітів, зберігання закритого ключа зашифрованим фразою.

**Керування ключами.** Створення — `hub_client.py keygen` (фраза ≥ 12 символів; шлях у репозиторії
відхиляється). Резервна копія закритого ключа — офлайн, у зашифрованій копії (ЛР15): **втрата ключа =
втрата всіх звітів** (сервер принципово не може допомогти). Компрометація — новий ключ, публікація
нового `.pub`, повідомлення тестерам.

**Чого E2EE не вирішує:** метадані видно серверу; автентичність автора тримається на довірі до
сервера (підпис тестера власним ключем — поза межами, обмеження нижче).

## 3. Серверна система верифікації даних — хеш-ланцюг (п. 8–9)

**Що потребує незмінності історії:** публікації релізів (версія → SHA-256 архіву й `.asi`) — якщо хтось
непомітно змінить хеш «офіційного» релізу на сервері, гравці звірятимуть файли з фальшивкою; прийом
звітів тестерів — квитанція доводить, що звіт був прийнятий саме таким і в цьому порядку.

| Поле блока | Зміст |
|---|---|
| `idx` | порядковий номер (0 — genesis) |
| `ts` | час UTC |
| `kind`, `ref` | `genesis` / `release` (версія) / `report` (`report_id`) |
| `payload_sha256` | SHA-256 канонічного JSON запису релізу або конверта звіту (самі дані в блоці не дублюються) |
| `prev_hash` | хеш попереднього блока (у genesis — 64 нулі) |
| `hash` | SHA-256 канонічного JSON усіх полів вище |

- Блок дописується **в тій самій транзакції SQLite**, що й запис даних: запис без блока неможливий.
- Клієнт отримує **квитанцію** — номер і хеш блока.
- **Перевірка** (`GET /api/v1/ledger/verify`, скоуп `ledger:read`; локально `hub_ledger.py verify`):
  безперервність номерів, хеш кожного блока, `prev_hash`, а також звірка `payload_sha256` з поточними
  даними: виявляється змінений блок, змінений після фіксації реліз чи звіт, зниклий запис і запис,
  доданий у базу в обхід журналу.
- **Якорення.** Хто контролює базу, той може перерахувати весь ланцюг заново (як у вправі п. 4). Тому
  голова ланцюга (`hub_ledger.py head`) після кожного релізу фіксується поза сервером — у записі
  `docs/changelog.md` репозиторію (git і GitHub). Перерахований ланцюг матиме іншу голову.
- **Чому без Proof of Work і консенсусу.** Учасник один (сервер супроводжувача): PoW лише сповільнив
  би запис, не додавши захисту від власника бази; роль «розподіленої копії» виконує якір у git. PoW і
  ціну переписування історії показано у вправі `labs/lab13_14/blockchain_demo.py`.

## 4. Відмінність механізмів

E2EE обмежує, **хто може прочитати** дані (лише супроводжувач). Хеш-ланцюг показує, **чи змінювали**
вже зафіксовану історію (релізи, факти прийому звітів). Жоден не замінює інший: ланцюг не приховує
даних, E2EE не захищає від видалення чи підміни запису сервером.

## 5. Обмеження

- Метадані звітів відкриті серверу; розмір шифротексту видає приблизний розмір пакета.
- Автор звіту засвідчений сервером (TLS + токен + `submitter` в AAD), а не власним підписом тестера.
- Ланцюг без якоря не захищає від повного перерахунку власником бази; якір — після релізів.
- Втрата закритого ключа отримувача робить усі звіти нечитабельними — потрібна офлайн-копія (ЛР15).
