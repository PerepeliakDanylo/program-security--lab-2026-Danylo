## 2. Перевірка готовності до релізу (п. 7)

`python tools/release/release_tools.py check --osv` (код 1 — реліз заблоковано):

| Що перевіряється | Як |
|---|---|
| Немає тестових облікових записів, тимчасових маршрутів, засобів розробки | у коді сервера немає тестових маршрутів; тестові клієнти живуть лише в тимчасовій базі самотесту; робочі клієнти — `hub_admin.py list-clients` перед релізом |
| Немає секретів у коді й репозиторії | відстежуваних `*.key`, `*.pem`, `*.secret`, `*.db`, копій, журналів, `.venv` немає; шаблони вмісту: PEM закритого ключа, `dhs_…`, `dha_…`, `client_secret = "…"`, токени GitHub |
| Налагоджувальні режими вимкнено | `HubConfig`: `insecure_http = false`, `host = 127.0.0.1`, `log_level = info`, токен ≤ 10 хв; постачальний INI мода — без `ForceAnimReloadRateOffset` і без `LogLevel = debug` |
| Коректність конфігурації | `HubConfig.validate()` на значеннях за замовчуванням |
| Версії залежностей зафіксовано | `requirements.txt` обох інструментів — `пакет==версія`; збіг зі встановленою |
| Немає відомих критичних вразливостей | запит до OSV (`api.osv.dev`) для кожної зафіксованої залежності |
| Відтворюваність складання й розгортання | дві збірки HEAD → однаковий SHA-256; самоперевірки `drs_hub` і `drs_release` проходять; розгортання — `README.md` інструментів |

## 4. Довгострокова підтримка (п. 9)

**Звідки дізнаємося про вразливості:**
- власний код — `SECURITY.md` (приватне повідомлення на GitHub або ПП RedziYT на Nexus), коментарі й баг-репорти на
  Nexus, журнали сервера (`alert.raised`), огляд коду перед кожним релізом;
- залежності — щомісячно `release_tools.py check --osv`; за бажанням власника — сповіщення Dependabot у налаштуваннях
  репозиторію; ScriptHookRDR2 — сторінка автора SDK; оновлення гри — після кожного патча RDR2 запуск мода з `LogLevel = info`.

**Підготовка, перевірка й встановлення оновлень:**
1. Виправлення в гілці → самоперевірки (`hub_selftest.py`, самотести `drs_release`) і для мода — група змін `TESTPLAN.md`
   (обсяг PATCH, політика §12).
2. `release_tools.py check --osv` без блокерів.
3. **Резервна копія перед оновленням** (`hub_backup.py create --label pre-update`).
4. Реліз: тег, артефакт, SHA-256, SBOM (інструменти) / архів, паспорт, Nexus (мод); запис у `changelog.md`; якір голови
   хеш-ланцюга після публікації релізу.
5. Оновлення сервера: зупинити → `git checkout tools-v<нова>` → `pip install -r requirements.txt` → старт →
   `hub_ledger.py verify` і `hub_monitor.py verify`.

**Якщо оновлення невдале:** сервер — зупинити, `hub_backup.py restore <копія pre-update> --target … --force`,
`git checkout tools-v<попередня>`, старт, перевірки; мод — гравець повертає попередній `.asi` (рекомендація сторінки
мода: зберігати `.asi.<версія>.bak`), а сам плагін за невдалого резолвінгу лишає гру незмінною (F-12).

**Які версії підтримуються:** мод — лише остання 1.2.x (старші — «оновіться»); інструменти — остання 1.0.x; після виходу
MINOR (1.1.0) попередня гілка отримує лише виправлення безпеки ще 3 місяці. Збірка гри — перевірена `1.0.1491.50`,
нові — за принципом «мод перевіряє себе на кожному старті».

**Завершення підтримки (п. 9, теорія):**
1. Оголошення щонайменше за 30 днів: сторінка мода (Posts, опис), `README.md`, `SECURITY.md` (таблиця версій).
2. Останній реліз із примітками «без подальших оновлень» і інструкцією видалення (мод — видалити `.asi` і `.ini`).
3. Виведення сервера: `disable-client` для всіх клієнтів (токени відкликаються), остання **зашифрована** копія
   (зберігати 1 рік), обробити й видалити звіти тестерів, знищити закритий ключ звітів і ключ TLS, безпечно видалити
   теку даних; ключі підпису релізу — зберегти офлайн, доки потрібна перевірка старих релізів, або оголосити їх
   відкликаними; журнали безпеки — архів 1 рік.
4. Репозиторій — режим «Archived» на GitHub (читання лишається, нові зміни неможливі).
