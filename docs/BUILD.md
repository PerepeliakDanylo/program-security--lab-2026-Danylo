## 2. Звідки береться кожен сторонній файл

Це місце, де найлегше помилитися, тому походження вказане пофайлово. Потрібно **чотири** файли
з **трьох** джерел. Жоден із них не комітиться в репозиторій.

| Куди покласти | Що саме | Звідки |
|---|---|---|
| `inc/main.h` | експорти ScriptHook: `scriptRegister`, `scriptWait`, `nativeInit`/`nativePush64`/`nativeCall`, `worldGetAllPeds`, `keyboardHandlerRegister` | архів **ScriptHookRDR2 SDK 1.0.1207.73** (Alexander Blade), файл `inc/main.h` |
| `inc/types.h` | `Ped`, `Player`, `Hash`, `BOOL`, `Vector3` | той самий архів, файл `inc/types.h` |
| `inc/natives.h` | оголошення нативів за іменами | **згенерувати** на `https://alloc8or.re/rdr3/nativedb/` → кнопка **Generate natives.h** |
| `lib/ScriptHookRDR2.lib` | імпорт-бібліотека | архів **ScriptHook V2 2.0**, файл `sdk/ScriptHookRDR2.lib` |

**`inc/nativeCaller.h` з архіву Alexander Blade брати не треба — і не можна.** Його замінює
власний файл проєкту `src/NativeShim.h`. Причина в §2.2.

Три рішення в цій таблиці варті пояснення, бо вони не очевидні.

**Чому заголовки від Alexander Blade, а `.lib` — від V2 2.0.** В архіві ScriptHook V2 **2.0**
лежать лише `ScriptHookRDR2.dll` і `sdk/ScriptHookRDR2.lib` — заголовків там немає взагалі.
V2 за задумом автора зберігає ту саму архітектуру API, тому заголовки від Alexander Blade з
бібліотекою від V2 поєднуються штатно. Це не припущення: так само відповів сторонній модер, до
якого Дан звернувся з цим самим питанням — «main, natives і types від ScriptHook, лінкувати з
`.lib` від ScriptHookV2».

Перевірка цього рішення вбудована в процес: усі функції, які плагін бере з `main.h`, — це
`__declspec(dllimport)`-оголошення, і якщо в `.lib` від 2.0 бодай одного символу немає або він
має інший підпис, компонувальник скаже це поіменно (`LNK2019: unresolved external symbol`), а не
мовчки. Тихого провалу тут бути не може.

**Запасний варіант, якщо `LNK2019` усе ж виникне:** `sdk/main.h` з архіву **ScriptHook V2 1.1.1**
(в 1.1.1 заголовок ще був у складі). Він оголошує ширший набір експортів, ніж версія 2019 року.
Але ставити його першим вибором не варто — див. §2.1.

**Чому `natives.h` генерується, а не береться з архіву SDK.** У SDK 1.0.1207.73 є свій `natives.h`,
але він зроблений під збірку **1207** 2019 року. Гра — **1.0.1491.50**. Генератор на `alloc8or.re`
віддає поточну базу (≈7100 нативів, у JSON є позначки `added in build 1491.50`). Саме її беремо.
Адреса — `rdr3`, **не** `rdr2`: сторінки `alloc8or.re/rdr2/nativedb/` не існує.

**Чому не годиться `getGameVersion()` із SDK.** Заголовки обох SDK оголошують `enum eGameVersion`
із замороженим переліком: у Alexander Blade це `VER_1_0_1207_60_RGS`/`VER_1_0_1207_69_RGS`, у V2
1.1.1 — `VER_1_0_1491_18_RGS`/`VER_1_0_1491_18_STEAM`. Збірки **1491.50** немає в жодному з них.
Функція повертає порядковий номер зі свого переліку, і зіставити його з рядком `1.0.1491.50`, який
гравець пише в `[Versions]`, неможливо. Тому номер збірки читається з ресурсу `VS_VERSIONINFO`
самого `RDR2.exe` (модуль `src/GameBuild.cpp`) — це ті самі чотири числа, що Windows показує у
властивостях файлу, і працюють вони й після патча, про який SDK ще не знає.

### 2.1 Чому саме заголовок 2019 року, а не той, що від V2

Плагін використовує з `main.h` рівно сім речей: `scriptRegister`, `scriptUnregister(HMODULE)`,
`scriptWait`, `keyboardHandlerRegister`, `keyboardHandlerUnregister`, трійку
`nativeInit`/`nativePush64`/`nativeCall` і `worldGetAllPeds`. **Усі сім є в обох заголовках, з
однаковими сигнатурами.** Ширший набір експортів у V2 (`getStaticPtr`, `switchLabel`,
`getCommandFromHash`, `worldGetAllBlips`) проєкту не потрібен жодним рядком.

За рівної придатності вирішують дефекти. У `sdk/main.h` з архіву V2 1.1.1 їх два, і обидва — в
одному рядку:

```
IMPORT void* getCommandFromHash(uint64_t hash);
```

1. Перед `IMPORT` стоять два символи U+FEFF (BOM усередині тексту). MSVC може впасти на них із
   `C2018`/`C2059`.
2. `uint64_t` — тип із `<stdint.h>`, а файл підключає лише `<windows.h>`, який його не гарантує.
   Можлива помилка `C2061: syntax error: identifier 'uint64_t'`.

У заголовку від Alexander Blade цього рядка немає взагалі, тож немає й обох проблем. Тому він і
стоїть першим у таблиці: однакова придатність, менша поверхня для відмови.

**Якщо все ж береш `main.h` від V2** — і компілятор лається на цей рядок, видали рядок цілком.
Нічого не зламається: `getCommandFromHash`, `switchLabel` і `getStaticPtr` плагіном не
викликаються.

### 2.2 Чому `nativeCaller.h` із SDK не використовується

Згенерований `natives.h` і `nativeCaller.h` 2019 року **несумісні між собою**. Три конкретні
причини, кожна з яких сама по собі зупиняє збірку:

1. **`invoke<void>` не компілюється.** Згенерований заголовок викликає `invoke<void>(…)` приблизно
   **4000** разів. Тіло шаблона з `nativeCaller.h` закінчується рядком
   `return *reinterpret_cast<R*>(nativeCall());`, який за `R = void` некоректний. Старий
   `natives.h` 2019 року цієї проблеми не мав, бо користувався `invoke<Void>` з великої літери
   (`typedef DWORD Void`); генератор так не робить.
2. **У згенерованому `natives.h` немає жодного `#include`.** Він розрахований на те, що типи й
   `invoke<>` уже видимі в точці підключення.
3. **Бракує типів-дескрипторів.** `AnimScene`, `Prompt`, `ItemSet`, `Volume`, `PersChar`,
   `PropSet`, `Promise`, `Item` — їх у `types.h` 2019 року немає. Пропущений тип дає помилку
   компіляції навіть якщо плагін той натив не викликає: кожне тіло в цьому заголовку —
   `__forceinline`-функція, яку компілятор зобов'язаний перевірити.

`src/NativeShim.h` закриває всі три: додає типи, дає `invoke<>` з гілкою `if constexpr` для `void`
і підключає `main.h` та `types.h` у правильному порядку. Він **наш**, лежить у репозиторії й
підлягає рев'ю. Правило, що з цього випливає: сторонні заголовки не редагуються ніколи; усе, що
треба дописати, дописується в `NativeShim.h`.

Порядок підключення в `GameApi.cpp` фіксований і має значення:

```cpp
#include "inc/main.h"
#include "inc/types.h"
#include "NativeShim.h"
#include "inc/natives.h"
```

### 2.3 Підсумкова розкладка

```
inc/
  main.h              <- AB SDK 1.0.1207.73, inc/main.h   (запасний: V2 1.1.1, sdk/main.h)
  types.h             <- AB SDK 1.0.1207.73, inc/types.h
  natives.h           <- згенерований на alloc8or.re/rdr3/nativedb/
lib/
  ScriptHookRDR2.lib  <- ScriptHook V2 2.0, sdk/ScriptHookRDR2.lib
src/
  NativeShim.h        <- наш, уже в репозиторії
```

`CMakeLists.txt` перевіряє всі чотири сторонні файли до початку збірки й на кожен відсутній друкує,
з якого саме архіву його взяти. Якщо конфігурація впала з переліком файлів — це ця перевірка, а не
помилка компіляції.

### 2.4 Походження та контрольні суми

Вимога SR-06 («версія й SHA-256 фіксуються й звіряються перед збіркою релізу») виконується
**тут**, а не у файлі всередині `inc/`: тека `inc/` не комітиться, тож запис у ній не був би
частиною репозиторію.

**Коли це обов'язково.** Суми потрібні перед **публічним релізом** — саме тоді твердження «бінарник
на Nexus зібрано з цього коду» має бути доказовим. Для приватної збірки й для перевірки в грі вони
не потрібні, і їхня відсутність не блокує нічого. Тому таблиця нижче порожня не через недогляд: її
заповнює той, хто робить реліз, на тій машині, де лежать завантажені архіви. Обчислити суму за
когось іншого неможливо в принципі — вона рахується з файлу, а не з опису файлу.

**Як заповнити — одна команда на кожен файл, PowerShell:**

```powershell
Get-FileHash -Algorithm SHA256 "$env:USERPROFILE\Downloads\ScriptHookRDR2_V2_2.0.zip"
Get-FileHash -Algorithm SHA256 "$env:USERPROFILE\Downloads\ScriptHookRDR2_SDK_1.0.1207.73.zip"
Get-FileHash -Algorithm SHA256 ".\inc\natives.h"
```

Для `natives.h` рахується сума **самого файлу**, а не архіву: він генерується сайтом на льоту, і
двічі згенеровані файли збігатимуться лише поки база не оновилася. Тому поруч із сумою обов'язково
записується дата генерації — вона й ідентифікує версію.

| Джерело | Версія | Офіційна адреса | SHA-256 |
|---|---|---|---|
| ScriptHookRDR2 V2 | 2.0 (`.lib`) | `https://www.nexusmods.com/reddeadredemption2/mods/1472` | *заповнити перед релізом* |
| ScriptHookRDR2 SDK (Alexander Blade) | 1.0.1207.73 (`main.h`, `types.h`) | `http://dev-c.com` | *заповнити перед релізом* |
| `natives.h` | згенеровано 2026-09-27 18:44 GMT | `https://alloc8or.re/rdr3/nativedb/` | *заповнити перед релізом* |

У `.gitignore` мають бути рядки `inc/` і `lib/` (у ньому вже є `*.lib`; тек це не покриває).

## 3. Збірка через CMake (основний шлях)

```powershell
cd "<корінь репозиторію>"
cmake -B build -G "Visual Studio 17 2022" -A x64
cmake --build build --config Release
```

Результат: `build\Release\DynamicReloadSpeed.asi`, а поруч тека `package\` із `.asi`, `.ini`,
`README.txt` і текою `presets\` — готова розкладка релізного архіву, рівно та, що описана в
`dist\README.txt`.

Якщо `.lib` лежить не там, де очікує скрипт:

```powershell
cmake -B build -G "Visual Studio 17 2022" -A x64 -DDRS_SCRIPTHOOK_LIB="C:\повний\шлях\ScriptHookRDR2.lib"
```

## 4. Збірка через Visual Studio

Відкрий `DynamicReloadSpeed.sln`, конфігурація **Release | x64**, `Build`.
Цей шлях існує для зручності; за розбіжності між `.vcxproj` і `CMakeLists.txt`
правильним вважається `CMakeLists.txt`.

### 4.1 Розбіжність, яка вже одного разу коштувала збірки

Обидва файли **зобов'язані** визначати `WIN32_LEAN_AND_MEAN` і `NOMINMAX`. Це не стиль:
`<windows.h>` оголошує функційні макроси `min(a,b)` і `max(a,b)`, а в `Script.cpp` і
`WeaponPatcher.cpp` він підключається **раніше** за `<algorithm>`. Без `NOMINMAX` препроцесор
розкриває макрос просто на виклику `std::max(` і компіляція падає з `C2589`/`C2059`.

До 2026-09-29 обидва макроси визначав лише `.vcxproj`. `CMakeLists.txt` — ні, тому падав саме
основний шлях збірки, а збірка з Visual Studio лишалася зеленою. Такий перекіс гірший за просту
помилку: «у мене збирається» і «у мене не збирається» одночасно правдиві, і причина не видно
з жодного з двох боків. Тепер визначення продубльовано в `CMakeLists.txt`
(`target_compile_definitions`). **Прибирати його не можна в жодному з двох файлів.**

Правило на майбутнє: будь-який прапорець компілятора чи макрос, доданий в один із цих файлів,
у той самий коміт додається й у другий.

## 5. Що робити з помилками компіляції в `GameApi.cpp`

**Це очікувано і це частина плану.** `GameApi.cpp` — єдиний файл, що знає про SDK,
і нативи в ньому викликаються **за іменем**, а не за хешем. Натив, якого в RDR2 немає,
дає помилку компіляції саме тут, а не мовчазну бездіяльність у грі.

Порядок дій на кожну таку помилку:

1. знайти правильне ім'я у згенерованому `inc/natives.h`;
2. звірити з `https://alloc8or.re/rdr3/nativedb/` — саме `rdr3`, адреси `rdr2` не існує;
3. виправити виклик і записати рядок у [`NATIVES.md`](NATIVES.md): ім'я, простір імен, хеш,
   сигнатура, де підтверджено;
4. якщо відповідника в RDR2 немає взагалі — поставити відповідний перемикач
   `DRS_HAVE_*` на початку `GameApi.cpp` у `0`, описати ситуацію в
   [`UNVERIFIED.md`](UNVERIFIED.md) і лишити цей сигнал вимкненим у INI.

Таблиця §3 `NATIVES.md` уже заповнена звіркою з базою `rdr3`, тому очікувана кількість таких
помилок — нуль. Якщо помилка все ж є, вона означає, що згенерований `natives.h` відрізняється від
бази, і це саме та розбіжність, яку треба зафіксувати в `NATIVES.md`.

**Чого робити не можна за жодних обставин:** «полагодити» помилку, підставивши вигаданий хеш
і викликавши `nativeInit` / `nativeCall` напряму. Такий код компілюється, запускається й нічого
не робить — це головний спосіб провалити весь проєкт, і вся конструкція `GameApi.cpp` існує
саме щоб його унеможливити.

## 6. Перша перевірка після збірки

1. Скопіювати `DynamicReloadSpeed.asi` і `DynamicReloadSpeed.ini` у корінь гри, поруч із
   `RDR2.exe` і `dinput8.dll` від ASI-лоадера.
2. Запустити гру, дочекатися завантаження збереження, вийти.
3. Відкрити `DynamicReloadSpeed.log` у корені гри. Мають бути, у цьому порядку:

```
RDR2 Dynamic Reload 1.0.0 starting
config: loaded from file, N warning(s), M weapon sections
game api: online check available, ...
game build: 1.0.1491.50
version check: no build list configured in [Versions], proceeding
waiting 8000 ms for the game to finish loading weapon data
memscan: regions=... scannable=... MB
resolver: 24 weapon names, 19 sectioned profiles to look for
resolver: AnimReloadRate signature=stock best offset=0x.... score=... -> accepted
snapshot: WEAPON_... AnimReloadRate = 1.3000  in-module: no
resolver: ready, N weapons and M sectioned profiles patchable
CALM applied: N fields written, 0 skipped
```

Рядок `game build:` — перша річ, яку треба перевірити: там має бути **1.0.1491.50**. Якщо там
`unknown`, читання ресурсу версії не спрацювало, і це окремий дефект, який треба усунути до
всього іншого (перевірка збірки без номера збірки не має сенсу).

Якщо замість резолвінгу є `resolver failed:` — це **не** аварія, а штатна відмова: гра при цьому
працює без змін. Рядок після двокрапки і є діагнозом. Далі — розділ 9 `DESIGN.md`.

## 7. Порядок доведення до робочого стану

Не намагайся зібрати й одразу перевірити все. Порядок із `DESIGN.md` §9:

1. розвідка нативів → `NATIVES.md` (виконано: таблиця §3 заповнена);
2. збірка з `Enabled = 0` — перевіряється лише те, що лог пишеться, конфіг читається
   й рядок `game build:` показує правильний номер;
3. `Enabled = 1`, але перевіряється **тільки** вивід резолвера: який офсет обрано, з якою
   оцінкою, скільки стволів підтвердили, `in-module: yes|no`, і чи знайдено п'ять стволів,
   яких немає у `weapons.ymt`;
4. лише після цього — `F8` (примусовий бій) на одному стволі й контрольне читання в лозі;
5. лише після цього — реальна перестрілка.
