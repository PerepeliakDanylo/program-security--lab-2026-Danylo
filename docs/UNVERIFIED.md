## Для чого цей документ

Тут лежить те, що **хотілося** мати, але що не підтверджене. Правило SR-19: непідтверджене
фіксується тут і **не викликається**. Документ існує, щоб «ми цього не знаємо» було записаним
фактом, а не забутим у процесі.

**Порожній `UNVERIFIED.md` — допустимий кінцевий стан.** Коли всі записи закриті, тут лишається
шапка й рядок «відкритих питань немає, станом на <дата>». Це нормально й це мета.

**Порожній через те, що записи повидаляли, — недопустимий стан.** Запис закривається лише
відповіддю: підтвердженням із `natives.h` і `rdr3 nativedb`, або рядком лога з першого прогону, або
свідомою відмовою від механізму. Видалення запису без відповіді — це тихе перетворення невідомого
на «вважаємо, що працює», тобто рівно той сценарій, проти якого написаний увесь комплект документів.
Закритий запис не видаляється: він лишається тут із датою, відповіддю й посиланням на артефакт, де
відповідь видно.

Формат кожного запису однаковий: **для чого хотілося → що використано натомість → яке саме питання
треба закрити → чим закривається**. Ідентифікатори іммутабельні; `A-x` збігаються з номерами
припущень у `DESIGN.md` і не перенумеровуються.

## 1. Сигнали й API

### U-01. Сигнал «розшук законом» — **ЗАКРИТО 2026-09-28**

| | |
|---|---|
| **Для чого хотілося** | Перестрілка з законом — найчастіший бій у грі. Ознака «гравця розшукують» мала б переводити стан у `COMBAT` навіть тоді, коли гравець тікає, не стріляє й ще не отримав шкоди |
| **Що використано натомість** | До 2026-09-28 — нічого: сигнал не опитувався, ключ `WantedByLaw` був мертвий |
| **Відповідь (2026-09-28)** | Натив знайдено: **`LAW::IS_LAW_INCIDENT_ACTIVE`**, хеш `0xAD401C63158ACBAA`, сигнатура `BOOL (Player player)`. Ключове — **простір імен `LAW`**, якого в `natives.h` 2019 року не існує взагалі: там ці функції лежать у `PURSUIT` під безіменними `_0x…`-заглушками, і саме тому попередній перебір їх не знайшов |
| **Чому не `GET_PLAYER_WANTED_LEVEL`** | Вона читається, але вся GTA-подібна родина навколо неї порожня: база позначає `SET_PLAYER_WANTED_LEVEL` і `CLEAR_PLAYER_WANTED_LEVEL` як `nullsub, doesn't do anything`. Читати число, яке підтримує система з непрацюючими сеттерами, — не сигнал. Відхилені також `GET_WANTED_SCORE` (число, не прапорець), `GET_BOUNTY` (лишається після погоні), `IS_PLAYER_BEING_ARRESTED` (надто пізня стадія) |
| **Де видно відповідь** | `NATIVES.md` §3.1 і §5; `GameApi.cpp`, `isPlayerWantedByLaw()`; перемикач `DRS_HAVE_WANTED = 1` |
| **Що лишилося перевірити прогоном** | Що сигнал справді вмикається під час погоні й гасне після її завершення — окремий пункт у `TESTPLAN.md`. Ключ `WantedByLaw` уже ввімкнений за замовчуванням, тож це зміна поведінки, а не косметика |

### U-02. Сигнал «активне Dead Eye» — **ЗАКРИТО 2026-09-28**

| | |
|---|---|
| **Для чого хотілося** | Dead Eye — однозначна ознака того, що гравець у бою (в мирній їзді його не вмикають). Дешевий і точний сигнал |
| **Що використано натомість** | До 2026-09-28 — нічого; ключ `[Signals] DeadEye = 0` |
| **Відповідь (2026-09-28)** | Натив знайдено: **`PLAYER::_IS_SPECIAL_ABILITY_ACTIVE`**, хеш `0xB16223CB7DA965F0`, сигнатура `BOOL (Player player)`. Провідне підкреслення — частина імені. У `natives.h` 2019 року він присутній як безіменний `_0xB16223CB7DA965F0` |
| **Пастка, зафіксована окремо** | Поруч лежить `_IS_SPECIAL_ABILITY_ENABLED` (`0xDE6C85975F9D4894`) — «чи відкрито Dead Eye взагалі». Він істинний майже всю гру, і плутанина між ними назавжди зафіксувала б стан `COMBAT`. Різниця між `_ACTIVE` і `_ENABLED` — не стилістична |
| **Де видно відповідь** | `NATIVES.md` §3.1; `GameApi.cpp`, `isDeadEyeActive()`; перемикач `DRS_HAVE_DEADEYE = 1` |
| **Що лишилося перевірити прогоном** | Значення за замовчуванням свідомо лишається `DeadEye = 0` до прогону — це **`AT-44b`**, і він сформульований так, що дає однозначну відповідь за один сеанс: 5 хвилин мирної їзди без Dead Eye (тега `deadeye` не має бути жодного разу), потім бій із Dead Eye (тег має з'явитися й згаснути). Підстава тримати `0` доти: натив підтверджено за документами, але не в грі, а хибнопозитивний тут тримав би мод у `COMBAT` посеред мирної їзди — рівно та поведінка, проти якої весь проєкт. Після успішного `AT-44b` значення змінюється одним рядком INI |

### U-04. Порядок викликів екранного оверлея

| | |
|---|---|
| **Для чого хотілося** | `OnScreenState = 1` має показувати поточний стан (`CALM`/`COMBAT`) просто на екрані — це те, чим перевірка стану стає наочною без читання лога |
| **Що використано натомість** | Реалізацію написано: `UIDEBUG::_BG_SET_TEXT_SCALE` → `_BG_SET_TEXT_COLOR` → `_BG_DISPLAY_TEXT`, а рядок будується через `MISC::VAR_STRING(10, "LITERAL_STRING", text)` |
| **Що саме не підтверджено** | Імена, хеші й сигнатури всіх чотирьох нативів підтверджені базою. Не підтверджені дві речі: **порядок** цих трьох викликів і значення `flags` у `VAR_STRING`. У базі немає коментаря, який описував би послідовність; вимога «текст має походити з `VAR_STRING`» — літеральний коментар на самому нативі, а от `10` і `"LITERAL_STRING"` виведені з прикладу використання в коментарі до іншого натива |
| **Чим закривається** | Прогоном `AT-49`: або текст видно, або ні. Якщо ні — `AT-49a` задає рівно три варіанти перебору, по одному за прогін, і кожен результат записується сюди. Перебір скінченний: після третього варіанта запис закривається відповіддю «не вдалося», а не лишається відкритим |
| **Запасний шлях і його ціна** | ScriptHookRDR2 **V2** додає власні текстові команди, яких немає в базі `rdr3`: `SET_TEXT_FONT` (`0x3EDE2F10`) і `SET_TEXT_JUSTIFICATION` (`0x1B929974`) — 32-бітні хеші, описані на сторінці V2. Вони працюють тільки під V2, тож їх використання перетворило б необов'язковий налагоджувальний оверлей на жорстку залежність усього мода від конкретної реалізації ScriptHook. Ціна непропорційна вигоді, тому це `AT-49b` — окреме свідоме рішення, а не наступна спроба за замовчуванням |
| **Наслідок, якщо не закрити** | Оверлей нічого не малює. Пам'ять не зачіпається, гра не змінюється, стан усе одно пишеться в лог на кожному переході. Тому `OnScreenState = 0` у постачальному INI і тому це не блокер |

### U-03. Чи існує `getGameVersion()` у ScriptHookRDR2 SDK — **ЗАКРИТО 2026-09-28**

| | |
|---|---|
| **Для чого хотілося** | FR-24 вимагає вивести в лог визначену збірку гри; FR-27 і SR-18 будують на цьому перевірку збірки проти `[Versions]`. Для обох потрібне джерело номера збірки, отримане від SDK, а не від самого плагіна |
| **Що використано натомість** | Нічого визначеного. Ім'я `getGameVersion()` узято з прототипу ТЗ **із приміткою «перевірити, що саме експонує SDK»** |
| **Відповідь (2026-09-28)** | Функція **існує** — вона оголошена в обох SDK. Але вона **не придатна** для того, задля чого була потрібна. Обидва заголовки віддають порядковий номер із замороженого переліку: Alexander Blade 1.0.1207.73 — `VER_AUTO, VER_1_0_1207_60_RGS, VER_1_0_1207_69_RGS`; ScriptHookRDR2 V2 1.1.1 — `VER_AUTO, VER_1_0_1491_18_RGS, VER_1_0_1491_18_STEAM`. Збірки **1.0.1491.50**, на якій іде розробка, немає в жодному переліку, тож функція поверне `VER_UNK` або сусідню константу, а зіставити ціле число з рядком `1.0.1491.50` у `[Versions]` неможливо в принципі |
| **Ухвалене рішення** | Залежність **знята**, а не задоволена. Номер збірки читається з ресурсу `VS_VERSIONINFO` самого `RDR2.exe` — модуль `src/GameBuild.cpp`, структура `VS_FIXEDFILEINFO`, поля `dwFileVersionMS`/`dwFileVersionLS`. Це ті самі чотири числа, що Windows показує у властивостях файлу, вони не залежать від SDK і лишаються правильними після патча гри, про який SDK ще не знає. Перемикач `DRS_HAVE_GAME_VERSION` із `GameApi.cpp` прибраний: перевірка більше не може бути «недоступною» |
| **Де видно відповідь** | `docs/BUILD.md` §2 (перелік і причина), `src/GameBuild.h` (шапка з обома переліками `eGameVersion`), рядок лога `game build: 1.0.1491.50` з першого прогону — `TESTPLAN.md`, AT-01 |
| **Що лишилося перевірити прогоном** | Рівно одне: що рядок `game build:` друкує `1.0.1491.50`, а не `unknown`. Це AT-01. Доти реалізація вважається написаною, але не підтвердженою |

## 2. Припущення з `DESIGN.md`

Чотири припущення, на яких стоїть шар пам'яті. Формулювання й номери — з `DESIGN.md`; тут вони
зібрані разом із тим, чим саме закриваються. Жодне з них не перевірене: коду немає, прогону немає.

### A-1. Ім'я зброї зберігається як joaat-хеш, а не як вказівник на рядок

| | |
|---|---|
| **Для чого хотілося** | Уся стратегія резолвінгу (AD-02) — шукати в пам'яті 4-байтовий joaat-хеш імені стволу. Хеш можна порахувати на етапі компіляції (`Joaat.h`), тобто в релізі немає жодного числа, прив'язаного до збірки гри |
| **Що використано натомість** | Обидві стратегії реалізуються одразу: **A** — пошук 4-байтового хеша; **B** (запасна) — пошук ASCII-рядка імені, потім пошук вказівника на нього. Резолвер журналює, яка спрацювала |
| **Питання, на яке треба відповісти** | Чи знаходить стратегія A хеш `joaat("weapon_rifle_varmint")` у закоммічених приватних областях процесу — і якщо ні, чи знаходить ціль стратегія B? |
| **Чим закривається** | Першим прогоном резолвера в режимі «тільки читання» (`DESIGN.md` §9, крок 3): у лозі має бути видно, яка стратегія дала результат. Спрацювала B → `DESIGN.md` §3.2 оновлюється, `[Memory]` дістає ще один крок пошуку |
| **Наслідок, якщо хибне** | Резолвінг відмовляє, мод переходить у `DISABLED_PERMANENT` і нічого не патчить (NFR-06). Гра лишається незміненою — це безпечна відмова, а не дефект |

### A-2. Цілі лежать поза образом модуля `RDR2.exe`

| | |
|---|---|
| **Для чого хотілося** | Визначає, де саме шукати й яку перевірку адреси застосовувати. Структури `CWeaponInfo` створює парсер RAGE із метафайлу під час завантаження, тобто вони мають лежати в купі процесу, а не в образі виконуваного файлу |
| **Що використано натомість** | Перевірка меж модуля як **обов'язкова** свідомо не застосовується: у первинній редакції SR-09 вона відкинула б кожну легітимну ціль і мод не патчив би нічого. Замість неї — перевірки `DESIGN.md` §4: закоммічена приватна область, поза образом плагіна, поза стеком потоку |
| **Питання, на яке треба відповісти** | Чи потрапляє хоч одна зрезолвлена адреса в образ головного модуля, тобто що показує рядок `in-module: yes\|no` для кожної цілі при першому прогоні? |
| **Чим закривається** | Рядком `in-module: yes\|no` у лозі резолвінгу — він обов'язковий за SR-09 саме для цього. Виявиться `yes` — перевірка меж модуля повертається як **додаткова**, і це тільки посилить захист |
| **Наслідок, якщо хибне** | Не ламає мод: перевірки §4 не залежать від цього припущення. Втрачається лише одна потенційна додаткова перевірка |

### A-3. Порядок полів у пам'яті збігається з порядком у XML-дампі, а чотири блоки станів лежать підряд з однаковим кроком

| | |
|---|---|
| **Для чого хотілося** | `CSectionedReloadInfo` містить чотири однакові за розкладкою блоки — `GoodCondition`, `WornCondition`, `GoodConditionOH`, `WornConditionOH`. Однаковий крок між ними дозволив би пропатчити всі чотири, зберігши співвідношення «чиста vs зношена зброя» (`PatchAllConditions = 1`) |
| **Що використано натомість** | Крок **не припускається, а шукається**: офсет `GoodCondition.LoopRate` знаходиться підписом зі стокових значень, крок визначається пошуком офсета з підписом `WornCondition` і перевіряється на третьому й четвертому блоці |
| **Питання, на яке треба відповісти** | Чи визначається крок між блоками станів, і чи однаковий він для всіх чотирьох блоків у всіх профілях? Що показує лог: крок знайдено чи `conditions: good only (stride unresolved)`? |
| **Чим закривається** | Логом резолвінгу. Крок не знайдено → патчиться лише `GoodCondition`, `PatchAllConditions` примусово стає `0`, у лог іде `conditions: good only (stride unresolved)` — і це записаний тут результат, а не аварія |
| **Наслідок, якщо хибне** | Деградація до `GoodCondition`. Різниця між чистою та зношеною зброєю лишається стоковою, тобто гірший, але коректний результат |

### A-4. П'ять відсутніх стволів узагалі існують у пам'яті як `CWeaponInfo`

**Найслабше припущення всього проєкту.** Раніше формулювалося як факт — виправлено в `DESIGN.md` §8.

| | |
|---|---|
| **Для чого хотілося** | `WEAPON_REVOLVER_LEMAT`, `WEAPON_REVOLVER_NAVY`, `WEAPON_PISTOL_M1899`, `WEAPON_REPEATER_EVANS`, `WEAPON_RIFLE_ELEPHANT` не мають запису `CWeaponInfo` у `weapons.ymt` — перевірено і на злитому файлі оверхолів, і на стокових даних. Жодна правка файлу їх не дістане. Якщо плагін дістає їх за joaat-хешем у пам'яті, це **найсильніший чесний аргумент** сторінки мода |
| **Що використано натомість** | Секції для п'яти стволів в INI є, але їхні `Calm_*` — оцінки з позначкою `TODO measure`, а `Combat_*` припускають рухомий рушій за замовчуванням `1.0` із позначкою `TODO verify`. Замірів немає, бо зброя була недосяжна |
| **Питання, на яке треба відповісти** | Чи існує структура `CWeaponInfo` для кожного з п'яти стволів у пам'яті процесу — тобто що друкує резолвер для кожного з них: адресу або `hash not found in memory`? |
| **Чим закривається** | Першим прогоном резолвера, остаточно. Резолвер зобов'язаний надрукувати рядок по кожному з п'яти. Адреса → твердження на сторінці мода стає правдивим. `hash not found in memory` → їх не дістане ніщо, і твердження **знімається зі сторінки**, а не пом'якшується формулюванням |
| **Наслідок, якщо хибне** | Мод працює як задумано для решти стволів; втрачається головний маркетинговий аргумент. Див. `MOD_PAGE_NOTES.md`, розділ «Не твердити» |
