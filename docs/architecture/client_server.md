## 1. Що є сервером, а що клієнтом

Проєкт складається з офлайн-частин (плагін `DynamicReloadSpeed.asi`, препроцесор `ymt-tweaker`,
інструмент супроводжувача `drs_release`) і **службового сервера супроводжувача** `tools/drs_hub`.
Сервер з'явився в ЛР10–11 для двох задач, які справді потребують спільного місця зберігання:

1. **Реєстр релізів** — незмінні записи «версія → файли → SHA-256 → тег/коміт → канал». Читає будь-який
   клієнт без токена (на хості супроводжувача; гравцям суми — у записі `[RELEASE]` і на сторінці мода),
   записує лише супроводжувач.
2. **Прийом діагностичних звітів тестерів** (лог плагіна, INI, перелік модів) — з ЛР13–14, зашифровано
   на боці тестера для супроводжувача.

Плагін і гра з сервером **не взаємодіють**: NFR-12 («жодних мережевих з'єднань») для компонентів
`asi` і `ymt-tweaker` лишається чинною. Сервер — окремий компонент `drs-hub`.

## 2. Розподіл функцій і даних (п. 10)

| Функція / дані | Сервер | Клієнт (`hub_client.py`) | Чому так |
|---|---|---|---|
| Хто звертається (автентифікація) | перевіряє секрет клієнта, видає й перевіряє токени | надсилає `client_id` + секрет, тримає токен у пам'яті | клієнт недовірений: рішення приймає сервер |
| Чи можна виконати операцію (авторизація) | роль → скоупи, скоуп маршруту, власник ресурсу | — (лише показує відповідь) | прихована кнопка чи перевірка в клієнті — не захист: запит формується в обхід клієнта |
| Реєстр релізів | зберігає, перевіряє схему, фіксує автора з токена | формує запис із файлів релізу | спільне джерело правди для всіх клієнтів |
| Облікові записи клієнтів, ролі | база сервера (лише SHA-256 секретів) | лише власний `client_id` | керування — локально на хості (`hub_admin.py`), мережевого API немає |
| Секрет клієнта | лише SHA-256 | файл поза репозиторієм / змінна середовища | сервер не може «розкрити» те, чого не зберігає |
| Токен доступу | лише SHA-256, строк, скоуп, стан відкликання | у пам'яті процесу | украдена база не дає робочих токенів |
| Ключ TLS сервера | тека даних сервера (поза репозиторієм) | — | |
| CA сервера (відкритий) | видає `hub_admin.py init` | `--ca ca_cert.pem` | клієнт довіряє лише цьому CA |
| Зміна темпу перезарядки, конфіг гравця, лог плагіна | **ніде на сервері** | **ніде в клієнті** | лишається в грі гравця (офлайн, NFR-12) |

## 3. Модель довіри

```
 [гравець / гра] ── без мережі ──  DynamicReloadSpeed.asi (офлайн, NFR-12)

 [супроводжувач] hub_client ─┐                         ┌─ hub_server ── drs_hub.db (поза репо)
 [тестер]        hub_client ─┼─ TLS 1.2+ (CA сервера) ─┤   рішення про доступ — ТУТ
 [аудитор]       hub_client ─┘     межа довіри         └─ hub_admin (лише локально на хості)
```

- **Клієнт недовірений**: його можна змінити, а запит — сформувати curl-ом. Тому роль, автор запису
  чи ідентифікатор власника з тіла запиту сервер **не бере до уваги**; невідомі поля тіла → `400`.
- **Мережа недовірена**: облікові дані й токени — лише через TLS; клієнт перевіряє сертифікат за
  CA сервера й ім'я хоста, тож підміна сервера («людина посередині») дає помилку перевірки.
- **Сховище сервера — вразливе для крадіжки**: тому в ньому лише SHA-256 секретів і токенів.

## 4. Мережева автентифікація (п. 11)

**Спосіб — OAuth 2.0, грант Client Credentials (RFC 6749 §4.4).** Кожен клієнт — програма з
`client_id` і випадковим секретом 256 біт (`dhs_…`), який генерує сервер (`hub_admin.py add-client`).

```
hub_client                                   hub_server
   │ POST /oauth/token                           │
   │ Authorization: Basic base64(id:секрет)      │  блокування? → 429 + Retry-After
   │ grant_type=client_credentials[&scope=…]     │  SHA-256(секрет) == збережений? (сталий час)
   │────────────────────────────────────────────▶│  скоуп ⊆ ролі?
   │ 200 {access_token: dha_…, token_type:Bearer,│  токен 256 біт → у базу лише SHA-256, +10 хв
   │      expires_in:600, scope:"…"}  no-store   │
   │◀────────────────────────────────────────────│
   │ GET /api/v1/… Authorization: Bearer dha_…   │  SHA-256(токен) → не відкликаний, не прострочений,
   │────────────────────────────────────────────▶│  клієнт увімкнений → суб'єкт; скоуп маршруту?
   │ 200 / 401 invalid_token / 403 insufficient_scope
```

| Рішення | Обґрунтування |
|---|---|
| Client Credentials, а не пароль людини | суб'єкти сервера — програми супроводу; паролі людей лишаються в офлайн-`drs_release` (ЛР4–ЛР6) |
| Без Resource Owner Password Credentials і Implicit | сучасні рекомендації OAuth (і проєкт OAuth 2.1) їх виключають; сервер відповідає `unsupported_grant_type` |
| Секрет лише в `Authorization: Basic` | RFC 6749 §2.3.1 рекомендує саме цей спосіб; секрет у тілі форми → `400 invalid_request` |
| Непрозорий токен, а не JWT | сервер і так перевіряє кожен запит у власній базі; непрозорий токен миттєво відкликається й не несе тверджень, які довелося б підписувати й перевіряти |
| Строк дії 10 хв, без токенів оновлення | украдений токен живе недовго; для Client Credentials токен оновлення не потрібен (RFC 6749 §4.4.3) — клієнт просто бере новий |
| У базі лише SHA-256 секрету й токена | урок інциденту Libraxis (розібраний у ЛР12, `labs/lab12/LIBRAXIS_ANALYSIS.md`): токени сеансів відкритим текстом у таблиці `sessions` дали нападнику доступ адміністратора. Повільна KDF для секрету не потрібна: він має повні 256 біт ентропії (на відміну від пароля людини, FR-70) |
| Відкликання | клієнт — власний токен (`POST /oauth/revoke`, RFC 7009); адміністратор — усі токени клієнта; вимкнення клієнта й ротація секрету відкликають їх автоматично |
| Перебір | 5 невдач поспіль для `client_id` → блокування 5 хв із подвоєнням до 60 хв; 20 невдач з адреси за 10 хв → `429`; лічильник ведеться для будь-якого рядка `client_id`, тому `429` не видає, чи існує клієнт |

## 5. Підтримання стану автентифікованого клієнта

Стан — **на сервері** (таблиця `tokens`: SHA-256, клієнт, скоуп, видано, діє до, відкликано). Клієнт
тримає сам токен лише в пам'яті й оновлює його за 30 с до закінчення строку; на `401 invalid_token`
(строк минув, відкликано) — одна повторна автентифікація. На диск клієнт токен не пише.

## 6. Авторизація на сервері

| Роль | Скоупи |
|---|---|
| `tester` | `reports:submit`, `reports:read:own` |
| `maintainer` | `releases:write`, `reports:read`, `ledger:read`, `metrics:read` |
| `auditor` | `ledger:read`, `metrics:read` |

| Маршрут | Доступ |
|---|---|
| `GET /api/v1/health` | публічний (без внутрішніх подробиць) |
| `POST /oauth/token`, `POST /oauth/revoke` | автентифікація клієнта (Basic) |
| `GET /api/v1/whoami` | будь-який дійсний токен |
| `GET /api/v1/releases`, `GET /api/v1/releases/{версія}` | публічний (автор запису не розкривається) |
| `POST /api/v1/releases` | `releases:write` |

Правила: (1) перевірка — у точці виконання кожного маршруту, до виклику обробника; (2) суб'єкт і роль
— лише з токена; (3) запитаний скоуп токена не ширший за роль (`invalid_scope`); (4) керування
клієнтами мережею недоступне взагалі — лише `hub_admin.py` на хості сервера.

## 7. Захист від атак на мережеву автентифікацію

| Атака | Захист |
|---|---|
| Повний перебір, словник, password spraying | секрети — 256 біт випадковості; блокування за `client_id` і за адресою |
| Credential stuffing | секрети генерує сервер — повторно використаних паролів немає |
| Перехоплення, «людина посередині» | лише TLS 1.2+; клієнт перевіряє CA і ім'я хоста; HTTP без TLS — лише loopback + прапорець |
| Повторне відтворення токена | строк 10 хв, відкликання, TLS (токен не видно в мережі) |
| Викрадення бази сервера | у базі лише SHA-256 секретів і токенів |
| Викрадення токена з журналу | у журнал пишеться лише відбиток (12 hex SHA-256), не токен і не секрет |
| Надмірна довіра клієнту | роль/автор з тіла ігноруються, невідомі поля → `400` |
| Розкриття будови сервера | помилки без стека, SQL і шляхів; заголовок `Server` без версії Python; `/health` без подробиць |
| Відмова в обслуговуванні простими засобами | межа тіла запиту (413), тайм-аут читання, `Content-Length` обов'язковий |

## 8. Трасування

FR-88 – FR-92 (`requirements.md` §2.16), SR-39 – SR-43, загрози TT-16 – TT-20; самоперевірка
`tools/drs_hub/hub_selftest.py` (кожен рядок таблиці §7 має відповідну перевірку).

## 9. Обмеження

- Сертифікат лише на `localhost`/`127.0.0.1`; доступ ззовні потребує сертифіката на ім'я хоста.
- Ключ TLS сервера в теці даних незашифрований (сервер стартує без людини); захист — ACL профілю.
- Блокування за `client_id` можна використати, щоб тимчасово заблокувати чужого клієнта.
- Прив'язки токена до клієнта (mTLS/DPoP) немає: украдений до закінчення строку токен працює.
