## 1. Призначення системи

У ванільній Red Dead Redemption 2 перезарядка зброї виконується швидко й аркадно. Повільна, деталізована перезарядка значно виграшніша для занурення під час полювання, мародерства та їзди верхи, але в перестрілці вона відчувається штучною та призводить до смерті гравця через механіку, а не через рішення.

`RDR2 Dynamic Reload` розв'язує цей конфлікт: поза боєм перезарядка повільна й реалістична, у бою — швидка, близька до ванільної. Перемикання відбувається автоматично, під час гри, без участі гравця.

Система складається з двох компонентів, що постачаються з одного репозиторію й можуть використовуватися окремо один від одного:

| Компонент | Технологія | Роль |
|---|---|---|
| `ymt-tweaker` | Python 3.8+, тільки стандартна бібліотека (`xml.etree.ElementTree`, `re`, `csv`) | Офлайн-препроцесор: переписує три числові поля у метафайлі `weapons.ymt`, формує CSV-звіт і готовий INI-конфіг для плагіна |
| `DynamicReloadSpeed.asi` | C++17/20, x64, MSVC `/MT`, ScriptHookRDR2 SDK | Рантайм-плагін: визначає стан бою та перемикає ті самі три поля напряму в пам'яті процесу гри |

Обидва компоненти працюють рівно з трьома числовими полями:

| Поле | Структура | Семантика | Напрям |
|---|---|---|---|
| `AnimReloadRate` | `CWeaponInfo` | Темп відтворення анімації перезарядки | менше = повільніше |
| `TimeBetweenBulletsInLoop` | `CSectionedReloadInfo` | Пауза між окремими набоями при поштучному заряджанні, секунди | більше = довше |
| `LoopRate` | `CSectionedReloadInfo` | Темп циклу вставляння одного набою | менше = повільніше |

## 2. Чому два компоненти, а не один

`weapons.ymt` читається грою **один раз** — під час завантаження — і розкладається у структури `CWeaponInfo` та `CSectionedReloadInfo` в оперативній пам'яті. Редагування файлу в рантаймі не дає жодного ефекту. Звідси поділ:

- статичну, наперед відому частину (калібровані значення для 24 стволів, діагностика злитих файлів, звіт) дешевше й безпечніше робити офлайн, у Python, де є повноцінний XML-парсер і немає обмежень реального часу;
- динамічну частину (перемикання профілів залежно від бою) можна зробити лише зсередини процесу гри, записом у пам'ять.

Плагін при цьому **не залежить** від препроцесора: він самодостатній і покриває сценарій «користувач встановив тільки `.asi`».

## 3. Межі проєкту

### 3.1 Входить до системи

- Читання, «лікування» та розбір `weapons.ymt` у форматі XML-подібного метафайлу (близько 88 000 рядків у типовому злитому файлі).
- Перезапис рівно трьох полів перезарядки у вихідному `weapons.ymt`.
- CSV-звіт по всіх стволах вхідного файлу: оригінальні значення, нові значення, стволи без конфігу, профілі без збігу.
- Експорт INI-конфігу для плагіна зі значеннями, знайденими у вхідному файлі (бойовий профіль) та з таблиці калібрування (мирний профіль).
- Діагностика дублікатів `CWeaponInfo` — типовий наслідок злиття кількох оверхолів зброї.
- Резолвінг хешованих (joaat) імен профілів перезарядки замість текстових.
- Рантайм-детекція бою за набором незалежних сигналів.
- Скінченний автомат `CALM → COMBAT → COOLDOWN → CALM` з миттєвим входом у бій і затриманим виходом.
- Патч трьох полів у пам'яті гри на переходах станів, зі знімком оригінальних значень і їх відновленням.
- Конфігурування всього — включно з параметрами резолвінгу (вікно офсетів, крок, пороги консенсусу) — через текстовий INI-файл.
- Лог-файл із конкретними значеннями кожної операції та опційний екранний оверлей стану.

### 3.2 Свідомо поза межами

| Поза межами | Обґрунтування |
|---|---|
| Робота в мультиплеєрі (Red Dead Online) | Проєкт орієнтований виключно на одиночну гру; при виявленні мережевої сесії плагін відновлює оригінали й переходить у постійний простій |
| Зміна `damage`, `recoil`, `spread`, ємності магазину та будь-яких інших полів `CWeaponInfo` | Сумісність зі сторонніми оверхолами зброї: проєкт перекриває лише тайминг перезарядки й не втручається в чужий баланс |
| Мережева взаємодія, телеметрія, автооновлення | Мод не має жодних мережевих функцій; єдиний запис на диск — власний лог поряд із DLL |
| Власний інсталятор | Встановлення — розпакування архіву в корінь гри; видалення — видалення двох файлів |
| Обхід або вимкнення античит-механізмів | Проєкт не є інструментом обходу захисту і не застосовується в мережевих сесіях |
| Редагування файлів гри під час її роботи | Безрезультатне за конструкцією гри (файл читається один раз) і небезпечне; уся динаміка — тільки в пам'яті |
| Підміна анімацій, моделей, звуків | Проєкт працює лише з числовими параметрами тайм-лайну перезарядки |
| Сумісність із модифікаціями, що самі переписують ті самі три поля в рантаймі | Два мод-и, що пишуть в одну адресу, дають недетермінований результат; такий конфлікт виявляється перевіркою «поточне значення = знімок» і призводить до відмови патчити конкретний ствол |

### 3.3 Відоме обмеження, що документується відкрито

`CWeaponInfo` — **глобальні дані гри**, спільні для всіх педів. Зміна темпу перезарядки діє не лише на гравця, а й на NPC: у стані `COMBAT` вороги перезаряджаються так само швидко, як гравець, у стані `CALM` — так само повільно. Механізму патчингу «тільки для гравця» на момент написання документа не знайдено. Обмеження приймається як компроміс і має бути явно зазначене у README та на сторінці мода; приховувати його заборонено.

## 4. Зацікавлені сторони

| Сторона | Роль | Основний інтерес |
|---|---|---|
| Гравець-користувач мода | Кінцевий споживач релізу з NexusMods | Мод не ламає гру, не крешить, працює одразу після розпакування, легко видаляється |
| Автор проєкту (RedziYT, Данило Перепеляк) | Розробник, супроводжувач, автор сторінки мода | Керованість змін, чесність тверджень на сторінці мода, можливість полагодити мод після патча гри без перезбірки |
| Мод-мейкер, що калібрує значення | Користувач `ymt-tweaker` | Прозорий звіт, детермінований підбір конфігу, діагностика злитого файлу |
| Автор стороннього оверхолу зброї | Суміжний розробник | Його значення `damage`/`recoil`/`spread` лишаються недоторканими; конфлікт обмежується таймінгом перезарядки |
| Спільнота NexusMods, модератори сторінки | Канал розповсюдження | Мінімальний і правдивий список вимог, відсутність прихованої функціональності та мережевої активності |
| ШІ-агент-виконавець (Antigravity IDE) | Реалізує код за специфікацією | Однозначна специфікація; заборона на вигадані нативи й офсети |
| Викладач і рецензент (ХНУ, «Безпека програмного забезпечення») | Оцінювач навчального артефакту | Відповідність ISO/IEC/IEEE 29148 і 42010, повнота DFD як основи моделі загроз |

## 5. Контекст використання

### 5.1 Сценарій А — гравець, лише плагін

Найпоширеніший випадок для користувачів NexusMods. Гра завантажила ванільні значення. Плагін сам підставляє повільні значення для `CALM`, а для `COMBAT` використовує значення, знайдені в пам'яті під час старту. Нічого редагувати не потрібно: свіже встановлення вже дає повільну перезарядку поза боєм і звичайну — у бою.

### 5.2 Сценарій Б — гравець, плагін + оброблений `weapons.ymt`

Гра завантажила повільні значення з файлу, обробленого `ymt-tweaker`. Плагін визначає, що знімок не збігається з еталонною таблицею ванільних значень, і бере `CALM` зі знімка, а `COMBAT` — з INI.

### 5.3 Сценарій В — гравець, плагін + сторонній оверхол зброї

Гра завантажила чужі значення (наприклад, файл, злитий із *Rededrunk's Ultimate Combat Overhaul* та *Catalogue Improvements*). Плагін працює в детермінованому режимі `Mode=manual`, повністю з власного конфігу, і торкається лише трьох полів перезарядки — баланс оверхолу зберігається.

### 5.4 Сценарій Г — мод-мейкер, офлайн-обробка

Користувач запускає `ymt-tweaker` на видобутому `weapons.ymt`, отримує оброблений файл, CSV-звіт і згенерований INI. Режим `--report-only` дозволяє отримати звіт та INI, не змінюючи `.ymt`.

### 5.5 Сценарій Д — супровід після оновлення гри

Після патча від Rockstar розкладка структур може змінитися, і резолвінг за консенсусом може не зійтися. Користувач править параметри пошуку в секції `[Memory]` в INI — за потреби задає примусовий офсет, надрукований логом, — і перевіряє лог: перезбірка плагіна не потрібна.

## 6. Зовнішні системи

| Зовнішня система | Тип взаємодії | Що з неї залежить |
|---|---|---|
| Red Dead Redemption 2 (одиночна гра, процес `RDR2.exe`, движок RAGE) | Плагін виконується всередині процесу; читає й пише пам'ять структур `CWeaponInfo` / `CSectionedReloadInfo` | Розкладка структур, адреси, набір і назви стволів; будь-яке оновлення гри може зламати резолвінг |
| ScriptHookRDR2 (SDK + рантайм) | Реєстрація скрипт-потоку, обробника клавіатури, доступ до нативних функцій. Номер збірки гри **не** береться звідси: його дає ресурс версії самого `RDR2.exe` | Єдина зовнішня залежність C++-компонента; походження кожного заголовка й `.lib` фіксується в таблиці §2.4 `docs/BUILD.md`: джерел три, а файлів чотири |
| ASI-лоадер (`dinput8.dll` зі складу ScriptHookRDR2) | Завантажує `.asi` у процес гри при старті | Без лоадера плагін не завантажується взагалі |
| RDR2 NativeDB (`alloc8or.re/rdr3/nativedb/`) | Довідник під час розробки | Джерело підтвердження кожного натива; використовується людиною та ШІ-агентом, не рантаймом |
| Сторонні оверхоли зброї (`weapons.ymt` від інших авторів) | Вхідні дані для `ymt-tweaker`; джерело значень, які плагін бачить у знімку | Дублікати `CWeaponInfo`, нестандартні імена профілів, хешовані імена |
| Lenny's Mod Loader (LML) | Опційний канал встановлення обробленого `weapons.ymt` у гравця | Потрібен лише для сценарію Б; плагін від нього не залежить і не вимагає його |
| NexusMods | Канал розповсюдження релізного архіву та сторінка мода | Вимоги до вмісту архіву, правдивість списку залежностей |
| GitHub (`PerepeliakDanylo/program-security--lab-2026-Danylo`) | Репозиторій вихідного коду й документації, ліцензія MIT | Публічність коду, історія змін |
| Visual Studio 2022 / MSVC, CMake | Складання C++-компонента (x64, Release, `/MT`, `/W4`) | Відтворюваність збірки на машині розробника |
| Інтерпретатор Python 3.8+ | Виконання препроцесора | Відсутність зовнішніх пакетів: усе з стандартної бібліотеки |

## 7. Процес розробки

Проєкт ведеться за **Specification-Driven Development**: специфікація є джерелом істини, код пише ШІ-агент (Antigravity IDE) під контролем розробника. Будь-яка зміна поведінки спочатку фіксується в специфікації, і лише потім реалізується. Агенту заборонено вигадувати нативні функції та офсети: кожен натив підтверджується в NativeDB і фіксується у `docs/NATIVES.md`, непідтверджене — у `docs/UNVERIFIED.md`. Детальні правила — у [`../policy/project_policy.md`](../policy/project_policy.md).
