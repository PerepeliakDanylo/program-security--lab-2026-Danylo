# drs_release — офлайн-інструмент супроводжувача релізів

Цільова тека в репозиторії: `tools/drs_release/`

Цей інструмент **не є частиною гри й не є частиною ASI-плагіна**. Його запускає
супроводжувач у власному терміналі, щоб керувати релізами мода DynamicReloadSpeed:
автентифікуватися, керувати доступом, (далі в ЛР6-ЛР8) ротувати ключі, підписувати збірку
й перевіряти цілісність. Пароль вводиться через `getpass` — так само, як це роблять `sudo`
чи `git` — тому **жодного перехоплення введення в процесі гри немає**.

## Файли

| Файл | Призначення | Лаба |
|---|---|---|
| `accounts.py` | ядро автентифікації (PBKDF2-верифікатор, блокування, журнал) + керування записами | ЛР4, ЛР5 |
| `authz.py` | політика доступу RBAC + ABAC + DAC, єдина точка рішення `authorize()` | ЛР5 |
| `drs_release.py` | CLI: `init`, `add-user` (бутстрап), `login` + сесія з перевіркою прав | ЛР4, ЛР5 |
| `README.md` | цей файл | ЛР4 |

Наступні лаби додають: TOTP і конвертне шифрування секрету (ЛР6), HMAC-цілісність файлу та
маніфест релізу (ЛР7), підписаний паспорт релізу (ЛР8).

## Залежності

Лише **стандартна бібліотека Python** (`hashlib`, `hmac`, `json`, `re`, `secrets`).
`cryptography` додається в ЛР6 окремим комітом `[POLICY]`.

## Використання

```
python drs_release.py init
python drs_release.py add-user owner1          # бутстрап: лише для порожнього сховища → роль owner
python drs_release.py login owner1
```

У сесії (права перевіряються в момент виконання кожної команди — меню не ховається):

| Команда | Хто може |
|---|---|
| `help`, `whoami`, `status`, `exit` | будь-хто після входу |
| `list-users`, `verify` | `viewer` і вище |
| `build-manifest` | `contributor` і вище |
| `sign <build>` | `maintainer` і вище, лише чистий `master` (ABAC) |
| `add-user <user> <role>`, `set-role <user> <role…>`, `rotate-key` | `owner` |
| `passwd [user]` | свій запис — будь-хто; чужий — лише `owner` (DAC) |

Критичні команди (`sign`, `add-user`, `set-role`, `rotate-key`, `passwd`) після 5 хв від
останнього введення пароля просять повторного підтвердження (step-up). Відмова завжди
однакова — «Операцію відхилено.»; причина (`rbac`, `abac-dirty`, `not-owner`,
`stepup-failed`) — лише в журналі аудиту. Останнього `owner` позбавити цієї ролі не можна.

Атрибути релізу для `sign` у ЛР5 читаються з `release.state.json`
(`{"branch": "master", "dirty": false}`); немає файла — стан вважається брудним, і підпис
відхиляється. ЛР7 замінює файл реальним станом `git`.

## Модель захисту автентифікації (стисло)

* Пароль → PBKDF2-HMAC-SHA256, 600 000 ітерацій, сіль 16 Б → майстер-секрет (не зберігається).
* У файлі лежить лише верифікатор = HMAC-SHA256(master, "drs-release/verifier").
* Перевірка пароля — стала за часом; 5 невдач → блокування 5 хв із подвоєнням до 60 хв.
* PBKDF2 рахується за будь-якої відмови — час відповіді нічого не видає.
* Запис файлу атомарний; імена лише `^[A-Za-z0-9_.-]{1,32}$`.

## Відомі обмеження

* Тайм-аути сесії перевіряються на кожній команді; заблокований `input()` примусово не
  закривається.
* Цілісність самого файлу облікових записів захищається HMAC у ЛР7.
