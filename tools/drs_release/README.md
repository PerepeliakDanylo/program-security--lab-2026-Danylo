# drs_release — офлайн-інструмент супроводжувача релізів

Цільова тека в репозиторії: `tools/drs_release/`

Цей інструмент **не є частиною гри й не є частиною ASI-плагіна**. Його запускає
супроводжувач у власному терміналі, щоб керувати релізами мода DynamicReloadSpeed:
автентифікуватися (з другим фактором), керувати доступом, (далі в ЛР7-ЛР8) підписувати збірку й
перевіряти цілісність. Пароль і код вводяться через `getpass` — так само, як це роблять `sudo`
чи `git` — тому **жодного перехоплення введення в процесі гри немає**.

## Файли

| Файл | Призначення | Лаба |
|---|---|---|
| `accounts.py` | ядро автентифікації (PBKDF2-верифікатор, блокування, журнал), керування записами, поля TOTP | ЛР4-ЛР6 |
| `authz.py` | політика доступу RBAC + ABAC + DAC, єдина точка рішення `authorize()` | ЛР5, ЛР6 |
| `crypto.py` | конверт секрету TOTP (AES-256-GCM + HKDF), TOTP RFC 6238, самоперевірка | ЛР6 |
| `drs_release.py` | CLI: `init`, `add-user` (бутстрап), `login` + сесія з перевіркою прав | ЛР4-ЛР6 |
| `requirements.txt` | `cryptography>=42.0` (виняток політики §9, окремий `[POLICY]` ЛР6) | ЛР6 |
| `README.md` | цей файл | ЛР4 |

Наступні лаби додають: HMAC-цілісність файлу та маніфест релізу з підписом (ЛР7), підписаний
паспорт релізу (ЛР8).

## Залежності

`accounts.py` і `authz.py` — лише **стандартна бібліотека Python**. `crypto.py` (і тому
`drs_release.py`) потребує пакета `cryptography` ≥ 42 — AES-GCM і HKDF у стандартній бібліотеці
немає, а власні реалізації криптографії заборонені:

```
python -m venv .venv
.venv\Scripts\activate            # Windows (PowerShell: .\.venv\Scripts\Activate.ps1)
pip install -r requirements.txt
python crypto.py                  # самоперевірка: "crypto.py self-test OK …"
```

## Використання

```
python drs_release.py init
python drs_release.py add-user owner1          # бутстрап: лише для порожнього сховища → роль owner
python drs_release.py login owner1             # пароль; для запису з TOTP — ще й «Код TOTP:»
```

У сесії (права перевіряються в момент виконання кожної команди — меню не ховається):

| Команда | Хто може |
|---|---|
| `help`, `whoami`, `status`, `exit` | будь-хто після входу |
| `list-users`, `verify` | `viewer` і вище |
| `enroll-totp [--force]` | будь-хто — лише для **власного** запису |
| `build-manifest` | `contributor` і вище |
| `sign <build>` | `maintainer` і вище, лише чистий `master` (ABAC) |
| `add-user <user> <role>`, `set-role <user> <role…>`, `rotate-key` | `owner` |
| `passwd [user]` | свій запис — будь-хто; чужий — лише `owner` (DAC) |

Критичні команди (`sign`, `add-user`, `set-role`, `rotate-key`, `passwd`, `enroll-totp`) після 5 хв
від останнього введення пароля просять повторного підтвердження (step-up). Відмова завжди
однакова — «Операцію відхилено.»; причина — лише в журналі аудиту. Останнього `owner` позбавити
цієї ролі не можна.

## Другий фактор (TOTP)

1. `enroll-totp` у сесії друкує рядок `otpauth://totp/...` — його ключ (`secret=…`, base32)
   додається в будь-який застосунок-автентифікатор (Google Authenticator, Microsoft Authenticator,
   Aegis…) як «ключ налаштування». Підключення завершується лише правильним кодом із застосунку.
2. Далі вхід просить пароль і **«Код TOTP:»**. Невірний код, той самий код удруге чи підмінений
   запис — загальне «Автентифікацію відхилено.» і невдала спроба (те саме блокування, що й за
   пароль). Кожен код приймається **один раз**.
3. `rotate-key` (власник) — нові ключі конверта, той самий секрет: автентифікатор не змінюється.
4. `passwd` свого запису переобгортає секрет під новий пароль — автентифікатор працює далі.
   `passwd <інший>` (owner) **скидає** TOTP того запису: секрет відкриває лише пароль власника
   запису, тож користувач після входу підключає TOTP знову.

Немає автентифікатора під рукою (лише для демонстрації): поточний код за ключем із URI —
```
python -c "import base64,sys,crypto; s=sys.argv[1]; print(crypto.totp_code(base64.b32decode(s+'='*(-len(s)%8))))" <КЛЮЧ>
```

## Модель захисту (стисло)

* Пароль → PBKDF2-HMAC-SHA256, 600 000 ітерацій, сіль 16 Б → майстер-секрет (не зберігається).
* У файлі лежить лише верифікатор = HMAC-SHA256(master, "drs-release/verifier").
* Секрет TOTP: AES-256-GCM під випадковим DEK; DEK обгорнуто KEK = HKDF-SHA256(master,
  info "drs-release/totp-kek"); AAD = ім'я; свіжий 12-байтовий nonce на кожне шифрування.
* Перевірка пароля — стала за часом; 5 невдач (пароль або код) → блокування 5 хв із подвоєнням до 60 хв.
* PBKDF2 рахується за будь-якої відмови — час відповіді нічого не видає.
* Запис файлу атомарний; імена лише `^[A-Za-z0-9_.-]{1,32}$`.

## Відомі обмеження

* Тайм-аути сесії перевіряються на кожній команді; заблокований `input()` примусово не закривається.
* Рядок `otpauth://` з ключем лишається в історії терміналу — очистіть її після підключення.
* Хто може **записувати** файл облікових записів, той може прибрати поле `totp` чи підмінити
  верифікатор; цілісність самого файлу захищає HMAC у ЛР7.
* Годинник: код дійсний ±1 крок (30 с); відведений назад системний час тимчасово відхиляє коди.
