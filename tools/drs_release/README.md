# drs_release — офлайн-інструмент супроводжувача релізів

Цільова тека в репозиторії: `tools/drs_release/`

Цей інструмент **не є частиною гри й не є частиною ASI-плагіна**. Його запускає
супроводжувач у власному терміналі, щоб керувати релізами мода DynamicReloadSpeed:
автентифікуватися (з другим фактором), керувати доступом, формувати й підписувати маніфест
релізу та перевіряти цілісність. Пароль і код вводяться через `getpass` — так само, як це роблять
`sudo` чи `git` — тому **жодного перехоплення введення в процесі гри немає**.

## Файли

| Файл | Призначення | Лаба |
|---|---|---|
| `accounts.py` | автентифікація (PBKDF2-верифікатор, блокування, журнал), записи, поля TOTP, HMAC-цілісність файла | ЛР4-ЛР7 |
| `authz.py` | політика доступу RBAC + ABAC + DAC, єдина точка рішення `authorize()` | ЛР5, ЛР6 |
| `crypto.py` | конверт секрету TOTP (AES-256-GCM + HKDF), TOTP RFC 6238, самоперевірка | ЛР6 |
| `integrity.py` | SHA-256-маніфест релізу, підпис і перевірка Ed25519, `genkey`, самоперевірка | ЛР7 |
| `drs_release.py` | CLI: `init`, `add-user` (бутстрап), `login`, `protect` + сесія з перевіркою прав | ЛР4-ЛР7 |
| `release_signing.pub` | **відкритий** ключ перевірки релізів (комітиться — це еталон) | ЛР7 |
| `requirements.txt` | `cryptography>=42.0` (виняток політики §9) | ЛР6 |
| `README.md` | цей файл | ЛР4 |

Локальні файли, які **ніколи не комітяться** (`.gitignore`): `drs_release.accounts.json`,
`drs_release.accounts.json.key` (ключ цілісності), `drs_release.audit.log`,
`drs_release.signing.key` (приватний ключ підпису), `.venv/`.

## Залежності

`accounts.py` і `authz.py` — лише стандартна бібліотека Python. `crypto.py` і `integrity.py`
потребують пакета `cryptography` ≥ 42:

```
python -m venv .venv
.venv\Scripts\activate            # Windows (PowerShell: .\.venv\Scripts\Activate.ps1)
pip install -r requirements.txt
python crypto.py                  # "crypto.py self-test OK …"
python integrity.py               # "integrity.py self-test OK …"
```

## Використання

Запускати з теки `tools/drs_release` (сховище й ключі лежать поруч зі скриптами).

```
python drs_release.py init                     # порожній файл облікових записів + ключ цілісності
python drs_release.py add-user owner1          # бутстрап: лише для порожнього сховища → роль owner
python drs_release.py login owner1             # пароль; для запису з TOTP — ще й «Код TOTP:»
python integrity.py genkey                     # один раз: пара ключів підпису релізів
```

У сесії (права перевіряються в момент виконання кожної команди — меню не ховається):

| Команда | Хто може |
|---|---|
| `help`, `whoami`, `status`, `exit` | будь-хто після входу |
| `list-users`, `verify <тека>` | `viewer` і вище |
| `enroll-totp [--force]` | будь-хто — лише для **власного** запису |
| `build-manifest <тека>` | `contributor` і вище |
| `sign <тека>` | `maintainer` і вище, лише коли репозиторій на `master` без незакомічених змін (ABAC) |
| `add-user <user> <role>`, `set-role <user> <role…>`, `rotate-key` | `owner` |
| `passwd [user]` | свій запис — будь-хто; чужий — лише `owner` (DAC) |

Критичні команди (`sign`, `add-user`, `set-role`, `rotate-key`, `passwd`, `enroll-totp`) після 5 хв
від останнього введення пароля просять повторного підтвердження (step-up). Відмова завжди
однакова — «Операцію відхилено.»; причина — лише в журналі аудиту.

## Реліз: маніфест, підпис, перевірка

Тека релізу — **поза відстежуваними файлами** (наприклад `..\..\build\release\` — `build/` ігнорується),
інакше вона сама робить дерево «брудним», і підпис буде відхилено.

```
build-manifest ..\..\build\release     # MANIFEST.sha256: «sha256  шлях» для кожного файла
sign ..\..\build\release               # MANIFEST.sha256.sig — лише якщо маніфест збігається з текою
verify ..\..\build\release             # «Перевірку пройдено…» або перелік: змінено / відсутній / зайвий
```

Стан репозиторію для `sign` береться з `git` (`rev-parse --abbrev-ref HEAD`, `status --porcelain`):
не `master`, є незакомічені зміни, git недоступний — підпис відхилено.

## Цілісність файла облікових записів

Поле `mac` у самому файлі = HMAC-SHA256 над рештою вмісту; ключ — `drs_release.accounts.json.key`.
Будь-яка розбіжність, відсутня мітка чи ключ, файл без ключа чи ключ без файла — повідомлення й
код виходу 2, у журналі `integrity-fail:*`; жодна команда з таким файлом не працює. Сховище з
ЛР4-ЛР6 (без ключа й мітки) один раз захищається командою `python drs_release.py protect`.
Свідомий «чистий старт»: видалити разом `drs_release.accounts.json` і `drs_release.accounts.json.key`.

## Другий фактор (TOTP)

`enroll-totp` друкує рядок `otpauth://totp/...`; ключ `secret=…` додається в застосунок-
автентифікатор, підключення завершується правильним кодом. Вхід далі просить пароль і код; код
приймається один раз; невірний чи повторений код — невдала спроба (те саме блокування).
`rotate-key` — нові ключі конверта, той самий секрет; свій `passwd` переобгортає секрет, `passwd`
чужого (owner) — скидає TOTP того запису.

## Відомі обмеження

* HMAC захищає від зміни файла тим, хто не має ключа (копія чи резервна копія файла, інший
  обліковий запис ОС, випадкове пошкодження). Хто має повний доступ до файлів супроводжувача
  (і файла, і ключа), той може переписати мітку — локально це не закривається. Приватний ключ
  підпису маніфесту лежить тут незашифрованим (лише `.gitignore`); ЛР8 додає над маніфестом паспорт
  релізу з окремим ключем RSA — зашифрованим паролем і поза текою репозиторію.
* На Windows права `0600` не діють — ключі захищає лише ACL профілю користувача.
* Журнал аудиту не захищений від редагування (логування й моніторинг — окрема тема курсу).
* Тайм-аути сесії перевіряються на кожній команді; заблокований `input()` примусово не закривається.
