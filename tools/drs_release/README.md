# drs_release — офлайн-інструмент супроводжувача релізів

Цільова тека в репозиторії: `tools/drs_release/`

Інструмент супроводжувача (не частина гри й не частина ASI-плагіна): автентифікація з другим
фактором, керування доступом, підпис і перевірка цілісності релізу та **паспорт релізу**. Запускається
у власному терміналі через `getpass` — жодного перехоплення введення в грі немає.

## Файли

| Файл | Призначення | Лаба |
|---|---|---|
| `accounts.py` | автентифікація, записи, поля TOTP, HMAC-цілісність файла | ЛР4-ЛР7 |
| `authz.py` | політика доступу RBAC + ABAC + DAC, `authorize()` | ЛР5, ЛР6, ЛР8 |
| `crypto.py` | конверт секрету TOTP (AES-256-GCM + HKDF), TOTP RFC 6238 | ЛР6 |
| `integrity.py` | SHA-256-маніфест релізу, підпис і перевірка Ed25519; файли паспорта в маніфест не входять | ЛР7, ЛР8 |
| `passport.py` | паспорт релізу: підпис і перевірка RSA-PSS (RSA-3072), ключі, шлях ключа поза репозиторієм | ЛР8 |
| `drs_release.py` | CLI: `init`, `add-user`, `login`, `protect` + сесія з перевіркою прав | ЛР4-ЛР8 |
| `release_signing.pub` | **відкритий** ключ перевірки маніфесту (Ed25519) — комітиться | ЛР7 |
| `release_passport.pub` | **відкритий** ключ перевірки паспорта (RSA) — комітиться | ЛР8 |
| `requirements.txt` | `cryptography>=42.0` | ЛР6 |

Ніколи не комітяться (`.gitignore`): `drs_release.accounts.json`, `*.accounts.json.key`,
`drs_release.audit.log`, `drs_release.signing.key` (приватний Ed25519), `.venv/`. Закритий ключ
паспорта `release_passport.key` (RSA, зашифрований паролем) у теці репозиторію взагалі не лежить —
він у `%USERPROFILE%\.drs_release\` або за шляхом `DRS_PASSPORT_KEY`; рядок у `.gitignore` — страховка.

## Залежності

`accounts.py`, `authz.py` — стандартна бібліотека; `crypto.py`, `integrity.py`, `passport.py` —
`cryptography` ≥ 42 (`pip install -r requirements.txt`).

## Основне використання

```
python drs_release.py init
python drs_release.py add-user owner1          # бутстрап → owner
python drs_release.py login owner1             # пароль [+ код TOTP]
python integrity.py genkey                     # один раз: ключі Ed25519 (маніфест), обидва тут
python passport.py genkey                      # один раз: RSA-3072 (паспорт); закритий, зашифрований
                                               # паролем, → %USERPROFILE%\.drs_release\, відкритий → тут
```

Команди сесії (права перевіряються в точці виконання):

| Команда | Хто може |
|---|---|
| `help`, `whoami`, `status`, `exit` | будь-хто після входу |
| `list-users`, `verify <тека>`, `check-passport <тека>` | `viewer` і вище |
| `enroll-totp [--force]` | будь-хто — лише для власного запису |
| `build-manifest <тека>` | `contributor` і вище |
| `sign <тека>`, `make-passport <тека> [версія]` | `maintainer` і вище, лише `master` без змін (ABAC) |
| `add-user`, `set-role`, `rotate-key` | `owner` |
| `passwd [user]` | свій запис — будь-хто; чужий — `owner` (DAC) |

Критичні команди після 5 хв від введення пароля просять повторного підтвердження (step-up).

## Паспорт релізу (ЛР8)

Паспорт — підписаний RSA-PSS JSON, що посвідчує **походження й умови** випуску: продукт, версію,
автора, домашню сторінку, тип ліцензії (**Freeware / MIT**) і SHA-256 маніфесту ЛР7. Один підписаний
об'єкт засвідчує і умови поширення, і точні байти збірки.

```
# у сесії maintainer (після build-manifest і sign):
make-passport ..\..\build\release_sample 1.2.1   → RELEASE_PASSPORT.json (+ .sig)
check-passport ..\..\build\release_sample         → «Паспорт дійсний: … ліцензія Freeware / MIT …»
```

- Паспорт видається лише на **актуальний** маніфест: якщо теку змінено після `build-manifest`,
  `make-passport` відмовляє (`make-passport-deny:stale-manifest`) — спершу `build-manifest` і `sign`.
  Самі файли паспорта в маніфест не входять, тож `verify` після `make-passport` їх «зайвими» не вважає.
- **Закритий ключ RSA** (`release_passport.key`) — зашифрований паролем PKCS#8 (OpenSSL читає його як
  звичайний зашифрований приватний ключ) і лежить **поза** текою репозиторію: типово
  `%USERPROFILE%\.drs_release\release_passport.key`, інший шлях — змінна `DRS_PASSPORT_KEY`. Якщо шлях
  ключа виявився всередині робочого дерева git, `genkey` і `make-passport` відмовляють (SR-34).
  **Відкритий ключ** (`release_passport.pub`) комітиться — це еталон перевірки.
- RSA-PSS обрано для паспорта як схему, сумісну з інфраструктурою відкритих ключів і командами
  OpenSSL (`openssl dgst -sign … -sigopt rsa_padding_mode:pss`); Ed25519 лишається для компактного
  підпису файлового маніфесту.
- `check-passport` перевіряє весь ланцюг: підпис паспорта → хеш маніфесту дорівнює засвідченому →
  файли теки збігаються з маніфестом. `verify` (ЛР7) додатково перевіряє підпис самого маніфесту
  (Ed25519). Повна перевірка збірки — обидві команди.

## Відомі обмеження

* Клієнтське середовище не є довіреним: паспорт і підпис **посвідчують автентичність** збірки, але
  не обмежують копіювання (модель Freeware/MIT цього й не вимагає).
* Найцінніший секрет — закритий ключ паспорта (RSA): зашифрований паролем і поза репозиторієм.
  Ключ маніфесту (Ed25519, ЛР7) лежить у теці інструмента незашифрованим (лише `.gitignore` і ACL
  профілю), тому довіра до релізу = паспорт **і** маніфест: самим украденим ключем маніфесту
  «справжній» реліз не підробити. Компрометація будь-якого ключа — нова пара й повторна публікація
  відкритого.
* На Windows права `0600` не діють — ключі захищає лише ACL профілю користувача.
* Решта обмежень — як у ЛР6/ЛР7 (журнал аудиту, тайм-аути сесії).
